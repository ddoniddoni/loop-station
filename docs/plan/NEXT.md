## 이전 작업 — Phase 0 오디오 시작·종료 안정화

**상태: 구현 완료/미검증.** 요구사항 `SYS-03`, 관련 `SYS-04`와 Phase 0 통과 기준. 이번 안정화 범위의 코드와 회귀 시나리오를 작성했고 린트·타입 검사·빌드·React Doctor를 확인했다. 실제 오디오·단위·E2E 검증은 사용자 중단 요청에 따라 보류한다.

- 실제 Worklet의 첫 오디오 블록 처리 응답을 받은 뒤 준비 완료로 전환한다. 처리 응답의 버전·샘플레이트·블록 길이를 확인한다.
- 파일 로딩/오디오 준비의 무응답을 구분해 안내하고 사용자가 취소·재시도할 수 있게 한다. 시간 제한은 시작 실패 감지에만 사용하며 루프 시계로 사용하지 않는다.
- 중복 시작·초기화·종료를 방지한다. 시작 취소·오류 정리·재시작이 겹쳐 이전 작업이 새 상태나 마이크/트랙을 정리하지 않도록 한다.
- 사용자 동작 전 오디오/마이크 생성 없음, 모니터링 OFF, 마이크 없이 테스트 신호 사용이라는 기존 경계를 유지한다.
- 수명·오류 경로의 회귀 테스트와 production Worklet 시작/종료 E2E를 작성한다. 기존 테스트 중단 요청은 유지하며 미실행을 통과로 표시하지 않는다.

수정 전 코드 점검 근거: `initialize()`는 노드 생성 후 첫 처리 응답 없이 끝나며 `isReady`는 노드 존재만 검사했다. `stopAudio()`는 `close()` 완료 전에 엔진 참조를 비우고, 초기화 실패 정리 후에는 이전 작업인지 다시 확인하지 않았다. 첫 처리 응답, 시작 15초 제한, 동일 초기화/종료 Promise 공유와 작업 번호 확인, 종료 실패 재시도를 추가했다. 실제 브라우저 재현은 미실행이다.

Phase 0 종료 판단에는 실제 production Worklet 로딩·처리, 중복 AudioContext 방지, dispose, 권한 거부·입력 해제 검증이 필요하다. 이번 구현만으로 Phase 0 전체를 완료로 바꾸지 않는다.

## 직전 구현 — Tap Tempo

**상태: 구현 완료/미검증.** Phase 1 / 요구사항 `CLK-01`, 상세 명세 5.4절의 4분음표 BPM 계약. 이번 브랜치에는 Tap Tempo만 추가하며 카운트인 코드는 별도 브랜치에 보존한다.

### 사용자 결과와 정책

- 상단 BPM 설정의 `TAP · 템포 맞추기`를 두 번 이상 누르면 BPM 입력칸에 제안값이 나온다. `설정 적용`을 눌러 기존 엔진 명령 경로로 반영한다. 준비되지 않은 오디오를 자동 시작하거나 마이크를 요청하지 않는다.
- 최근 최대 4개 유효 간격의 평균으로 정수 BPM을 계산한다. 범위는 40~240, 6/8·7/8도 4분음표 기준이다. 클릭 이벤트의 입력 시각은 제안값 계산에만 쓰고 Worklet 공통 시계를 대체하지 않는다.
- 250ms 미만은 마지막 유효 시각을 움직이지 않고 제외한다. 1,500ms 초과이면 이전 간격을 비우고 해당 Tap부터 다시 센다. 유효하지 않거나 역행한 시각은 제외한다. Enter/Space를 계속 누를 때 반복 입력을 막는다.
- 수동 BPM 입력·설정 적용·설정창 닫기·오디오 준비/잠금 상태 변경 때 Tap 기록을 초기화한다. 설정창을 다시 열면 현재 적용 BPM·박자를 표시한다. 적용 전 초안은 저장하지 않는다.
- 기존 루프·비운 루프의 복구 이력·녹음 준비·편집·저장소 잠금과 오디오 준비 여부를 그대로 따른다. 설정 적용 시 UI와 기존 엔진 모두 잠금을 확인한다. 카운트인 통합 후에는 동일한 프로젝트 잠금 경로를 사용하며 통합 검증이 필요하다.

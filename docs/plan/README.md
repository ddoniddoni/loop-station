# Loop Station 개발 계획

2026-09-26 사용자와 확인한 Phase 0~8 계획을 앞으로의 개발 기준으로 정리한다. 기능 하나씩 엔진·화면·저장 경로를 연결하고, 실제 검증 결과에 따라 단계 상태를 갱신한다.

계획은 구현 증거가 아니다. 세부 요구사항과 검수 기준은 상세 명세를 따르고, 현재 상태와 검증 결과는 진행 기록을 기준으로 판단한다. 범위나 순서를 바꾸면 관련 계획과 진행 기록을 함께 갱신한다. 사용자의 최신 지시가 우선한다.

## 전체 로드맵

| Phase | 목표 | 사용자에게 생기는 결과 |
|---|---|---|
| 0 | 오디오 기반 | 브라우저에서 안전하게 오디오를 시작하고 입력 상태를 확인한다. |
| 1 | 정확한 녹음과 반복 | 한 트랙을 정해진 박자와 길이로 녹음하고 반복한다. |
| 2 | 8트랙 기본 루프스테이션 | 여러 소리를 쌓고 되돌리며, 로그인 없이 작업을 저장·복구한다. |
| 3 | 편집·지연 보정·파일 입출력 | 녹음을 다듬고 프로젝트를 옮기거나 WAV로 내보낸다. |
| 4 | 이펙트·장면·공연 녹음 | 효과를 적용하며 루프 조합을 바꾸고 전체 공연을 녹음한다. |
| 5 | 리듬·MIDI·곡 구성 | 드럼과 악기로 루프를 만들고 컨트롤러·자동화로 곡을 연주한다. |
| 6 | 고급 오디오 처리 | 음정과 속도를 독립적으로 바꾸고 더 복잡한 루프를 다룬다. |
| 7 | 선택적 클라우드 | 선택한 프로젝트를 기기 간 동기화하고 결과를 공유한다. |
| 8 | 출시 검증 | 지원 브라우저·장치와 실제 동작 범위를 확인한 제품을 제공한다. |

- **Phase 0~3:** 기본 루핑 제품의 첫 출시 범위. 녹음 → 편집 → 저장·복구 → 파일 내보내기가 연결되어야 한다.
- **Phase 4~6:** 고급 연주·작곡 기능을 확장한다.
- **Phase 7:** 사용자가 선택할 때 활성화하는 클라우드 기능이다. 로컬 모드는 독립적으로 유지한다.
- **Phase 8:** 전체 출시 검증이다. 각 기능의 검증을 이 단계까지 미루는 뜻은 아니다.

## Phase별 개발 범위

### Phase 0 — 오디오 기반

- 앱·개발 환경, 환경 진단, 사용자 동작 기반 오디오 시작·종료, 마이크 권한과 장치 선택, 기본 OFF 모니터링을 구성한다.
- AudioWorklet 빌드·로딩과 오디오 프레임/박자 변환을 연결한다.
- 통과 기준: production에서 실제 Worklet 로딩, 중복 오디오 엔진 방지, 종료 시 자원 해제, 권한 거부 처리와 필수 검사 통과.

### Phase 1 — 한 트랙의 정확한 녹음과 반복

- 입력 채널·게인·미터·모니터링, PCM 녹음, 고정 길이, 첫 반복 전환, 재생·정지·취소를 연결한다.
- BPM·박자표·Tap Tempo·메트로놈·카운트인과 박자에 맞춘 실행 예약을 구현한다.
- 통과 기준: 44.1/48kHz의 정확한 녹음 프레임 수와 전환 경계, 클릭이 녹음에 섞이지 않음, 입력 끊김 처리, UI 타이머에 의존하지 않는 반복.

### Phase 2 — 8트랙과 복구 가능한 기본 제품

- 8트랙, 1/2/4/8마디 혼합 길이의 공통 시계, 오버더빙 세션, Undo/Redo/Clear, 트랙 믹서와 단축키를 연결한다.
- 첫 자유 녹음으로 템포 설정, 로컬 프로젝트 관리·자동 저장·복구, 첫 사용 안내와 자체 데모를 구현한다.
- 통과 기준: 원본 A와 입력 B의 A+B 및 Undo→A, 혼합 길이 장시간 동기, 새로고침 복구, 저장 실패 표시, 메모리 초과 거절과 기존 PCM 보존.

### Phase 3 — 편집·지연 보정·파일 입출력

- 입력 지연 보정, 파형 편집, Loop/One-shot/Gate, 시작·정지 방식, 자유 루프, 리버스·배속, 루프 자르기·늘리기를 구현한다.
- WAV 가져오기, 믹스·트랙별 WAV 내보내기, 프로젝트 ZIP, 공연 모드·비상 정지, 중단 복구 기록과 다중 탭 충돌 처리를 완성한다.
- 통과 기준: 지연 보정 후 처음·끝 소리 보존, WAV 샘플·헤더 검사, ZIP 내보내기→가져오기, 손상·누락·용량 부족 처리, 비상 정지 후 안전한 재개.

### Phase 4 — 이펙트·장면·공연 녹음

- 입력/트랙/마스터 효과, EQ·필터·다이내믹·딜레이·리버브·왜곡, Send/Return을 연결한다.
- Replace/Feedback, 소리 감지 녹음, 명시적으로 켠 최근 연주 버퍼, 여러 클립·장면·그룹, 내부 바운스와 전체 공연 녹음을 구현한다.
- 통과 기준: 장면의 동시 전환, 실제 효과 적용, 모니터 이중 출력과 자기 피드백 방지, 클릭 제외, 공연 녹음 누락 감지·복구.

### Phase 5 — 리듬·MIDI·곡 구성

- 드럼 패턴, 샘플 패드, 내부 악기, MIDI 클립·피아노롤·파일 입출력을 구현한다.
- MIDI Learn·풋 컨트롤·장치 프로파일, 자동 장면 전환, 연주 타임라인·자동화, 효과 프리셋·매크로, 사용자 지정 화면·세트리스트를 연결한다.
- 통과 기준: 장치 분리 후 음이 계속 울리지 않음, MIDI 장치 없는 환경의 내부 악기 동작, 자동화 재현, 무한 전환 방지, 설정 저장·복구. 실제 장비 미검증은 따로 남긴다.

### Phase 6 — 고급 오디오 처리

- 음정 유지 템포 변경, 길이 유지 음정 변경, 재생 중 BPM 전환, 변환 확정 후 오버더빙, 인트로·테일과 변조 효과를 구현한다.
- 외부 MIDI Clock을 검증하고, 성능·메모리 기준을 통과한 환경에서 최대 16트랙을 활성화한다.
- 통과 기준: 변환 주파수·길이 검사와 보컬/드럼/코드 실청취, 경계·처리 지연 보정, 재현 가능한 배포와 라이선스 확인, 변환 실패 시 원본 유지.

### Phase 7 — 선택적 클라우드

- 상세 명세의 Supabase 설계를 따라 로그인, 사용자별 프로젝트·비공개 에셋, 재시도 가능한 동기화, 충돌 사본과 삭제를 구현한다.
- 공유는 사용자가 선택한 마스터 렌더를 대상으로 하며 만료·철회를 지원한다.
- 통과 기준: 미인증/서로 다른 사용자 간 접근 차단, 업로드 실패·버전 충돌 복구, 공유 만료·철회, 원본 비공개와 비밀값 보호. 클라우드 환경변수 없이도 로컬 모드가 실행되어야 한다.

### Phase 8 — 출시 검증과 사용성

- 주요 데스크톱 브라우저, 터치·작은 화면·접근성, 저장소 부족·새로고침·장치 변경을 검증한다.
- 장시간 연주와 내보내기 부하, 오프라인·업데이트 보호, 필요한 PWA와 실제 배포 환경을 확인한다.
- 통과 기준: 상세 명세 10절의 검증과 전체 요구사항 상태 대조. 지원 환경·조건부 기능·알려진 제한을 명시하고, 미구현이나 미실행을 완료로 계산하지 않는다.

## 앞으로의 개발 방식

Phase 0 오디오 수명 보강과 Phase 1 Tap Tempo, 1/2/4/8마디 녹음 길이·v5 저장을 develop에 통합했다. 음성 보정 옵션과 브라우저 보고값 표시를 `feature/phase-1-input-processing`에 구현했으며 다음 작은 기능은 **반복 재생·정지의 실행 시점 선택**이다. 기능 테스트는 보류 상태다. 카운트인·키보드 연주·입력 채널·AUTO 모니터링은 각각 별도 브랜치에 구현·푸시되어 있으며 develop과 이번 브랜치에는 미통합이다. 구체적 범위와 브랜치별 상태는 `NEXT.md`를 따른다.

1. `AGENTS.md`, 이 문서, `NEXT.md`, `PROGRESS.md`를 읽고 현재 작업 트리와 관련 명세를 확인한다.
2. 사용자가 “다음 기능”을 요청하면 `NEXT.md`의 현재 작업을 선택한다. Phase 개발 시작 전에 최신 원격 develop을 확인하고 `feature/phase-<번호>-<작업>` 등 작업 브랜치를 만든다. 같은 작업 브랜치에서 구현 중인 항목은 이어서 처리하고, 기능 범위·요구사항 ID·검증 항목을 짧게 정리한다.
3. 한 작업에서 하나의 작은 기능을 엔진 → UI → 실제 오디오/저장 경로까지 연결한다. 인접 Phase의 선행 구현은 가능하지만 남은 항목을 누락하거나 해당 Phase 전체를 완료로 처리하지 않는다.
4. 알려진 치명적 오디오·저장 오류가 있으면 기능 확장보다 수정한다. 검증이 보류된 경우 기능 개발은 이어가되 보류 사실과 위험 범위를 기록한다.
5. 허용된 검사를 실제 실행하고, 구현과 검증을 구분해 `PROGRESS.md`에 기록한다. 사용자 테스트 중단 요청은 재개 지시 전까지 유지한다.
6. 이번 작업 결과를 반영해 `NEXT.md`의 현재 작업·후속 순서를 갱신한다. Phase 범위나 전체 순서가 바뀌면 이 문서도 갱신한다.
7. 해당 개발을 마치면 관련 파일만 골라 Conventional Commit을 만들고 원격 작업 브랜치에 push한다. 기존 사용자 변경과 다른 기능의 미커밋 변경을 섞지 않는다. 미실행 검증이 있으면 그대로 기록하며, commit/push와 Phase 전체 완료를 구분한다.

2026-09-26 사용자가 **Phase 시작 전 브랜치 생성 → 개발 → 개발 종료 후 커밋·푸시**를 상시 승인했다. 이후 해당 작업에 매번 재승인을 요청하지 않는다. merge, rebase, PR 생성, tag/release, 배포와 파괴적 Git 작업은 별도 요청 범위다. 테스트 중단 요청은 재개 지시 전까지 유지한다.

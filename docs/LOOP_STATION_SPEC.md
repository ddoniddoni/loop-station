# 웹 루프스테이션 개발 명세서

**대상:** Codex가 구현하는 Next.js + React 웹 애플리케이션  
**패키지 관리자:** npm  
**서버 DB가 필요한 경우:** Supabase  
**문서 작성 및 공식 자료 확인 기준일:** 2026-09-21  
**상태:** 개발 전 설계 문서. 아래 기능과 수치는 구현 요구사항과 검증 목표이며, 이미 구현하거나 측정했다는 뜻이 아니다.  
**임시 작업명:** Loop Station Web

## 0. 이 문서를 사용하는 방법

### 파일 배치

```text
프로젝트 루트/
├── AGENTS.md
└── docs/
    ├── LOOP_STATION_SPEC.md
    └── PROGRESS.md
```

`AGENTS.md`에는 상시 규칙만 둔다. 이 문서는 제품, 오디오 엔진, 데이터, 개발 계획, 검수의 단일 상세 명세다. `PROGRESS.md`는 실제 진행 상황만 관리한다. 생성된 문서 패키지는 앱 소스가 아니므로 다음 지시로 구현을 시작한다.

### Codex 첫 실행 프롬프트

```text
AGENTS.md, docs/LOOP_STATION_SPEC.md, docs/PROGRESS.md와 기존 저장소를 읽어줘.
Next.js, React, TypeScript, npm으로 이 웹 루프스테이션을 구현해줘.
Supabase는 클라우드 기능에서만 사용하고 로컬 모드를 우선해줘.

이번 작업은 Phase 0으로 한정해줘. 기존 코드가 있으면 보존하고 현재 상태부터 확인해줘.
화면 목업만 만들지 말고 사용자 클릭으로 시작하는 AudioContext,
실제 AudioWorklet 로딩, 오디오 프레임 기반 테스트 신호 처리와 환경 진단을 연결해줘.
마이크 권한 허용/거부 흐름과 기본 입력 모니터링 OFF를 구현해줘.

필요한 npm 스크립트와 테스트를 만들고 lint, typecheck, test, build를 실제로 실행해줘.
실행하지 못한 검증은 통과라고 하지 말고 이유를 기록해줘.
완료 후 PROGRESS.md에 변경 파일, 구현 결정, 검증 결과, 미완료 항목, 다음 작업을 남겨줘.
사용자 요청 없이 commit, push, 실제 배포, 유료 리소스 생성을 하지 마.
```

### 다음 작업 프롬프트

```text
AGENTS.md와 docs/PROGRESS.md를 읽고 직전 구현을 확인해줘.
상세 명세에서 다음 미완료 Phase의 관련 요구사항과 인수 기준을 읽어줘.
이번에는 그 Phase의 가장 작은 실행 가능한 기능 단위를 구현하고 실제 테스트해줘.
검증 없이 단계를 건너뛰거나 미완료 기능을 완료 처리하지 마.
오디오, 저장 데이터, 사용자 변경을 보존하고 진행 문서를 갱신해줘.
```

## 1. 제품 목표와 범위

### 1.1 제품 정의

마이크, 악기 입력, 가져온 샘플을 녹음해서 반복하고, 반복 위에 새 소리를 쌓아 한 사람이 여러 파트를 연주하는 **실제 라이브 루프스테이션**을 만든다. 장면 전환, 효과, 리듬, MIDI 제어, 저장, 내보내기까지 하나의 작업 공간에서 처리한다.

가장 먼저 완성할 흐름은 다음과 같다.

```text
사이트 접속 → 오디오 시작 → 입력 확인 → 1번 트랙 녹음
→ 녹음한 소리가 끊김 없이 반복 → 2번 트랙 추가
→ 오버더빙 → 실수한 레이어 Undo → 믹스 조절
→ 로컬 저장 → 새로고침 후 복구 → WAV 내보내기
```

첫 사용부터 계정 생성이나 클라우드 연결을 강제하지 않는다. 가상 패드의 색만 바뀌는 데모, 마이크 녹음 파일을 단순 반복하는 플레이어, 프론트엔드 외형만 있는 포트폴리오가 목표가 아니다.

### 1.2 “유명 제품의 기능을 넣는다”의 범위

2절의 공식 제품 자료에서 확인한 루핑 중심 기능을 통합한다. 해당 제품들의 모든 DAW 기능, 모든 전용 FX 알고리즘, 하드웨어 드라이버, 브랜드 화면을 1:1 복제한다는 의미는 아니다. 경쟁 제품에서 확인한 기능과 이 프로젝트의 독자적인 구현 사양을 분리한다.

**핵심 기능과 확장 기능은 최종 제품의 구현 대상이다.** 확장이라는 이유로 삭제하지 않는다. 다만 한 번의 Codex 실행으로 모두 만들지 않고 단계별로 구현한다. 브라우저와 외부 장치 지원에 좌우되는 기능은 조건부로 관리한다. 미충족 품질 게이트는 미완료로 남기고 허위 기능으로 대체하지 않는다.

### 1.3 기본 제품 결정

| 항목 | 기본 결정 |
|---|---|
| 사용자 | 보컬, 비트박스, 기타, 전자음악, 작곡 스케치를 하는 개인 연주자 |
| 핵심 환경 | 데스크톱 Chrome/Edge를 첫 검증 대상으로 삼고 Firefox/Safari는 기능별 검증 후 지원 표시 |
| 모바일 | 재생, 가져오기, 저장, 터치 연주를 단계적으로 지원. 백그라운드 녹음이나 동일한 저지연 성능은 보장하지 않음 |
| 화면 | 기본 8트랙 연주 패널, 클립 그리드, 믹서, 세부 편집기 |
| 데이터 | 프로젝트 메타데이터와 오디오 에셋 분리, 로컬 우선 |
| 입력 | 첫 버전은 하나의 물리 입력 장치. 같은 장치의 채널 선택은 지원되는 범위에서 제공 |
| 출력 | 기본 한 개의 스테레오 출력. 장치 선택, 별도 큐 출력, 다중 하드웨어 출력은 기능 감지 후 제공 |
| 기본 템포 | 120 BPM, 4/4, 1마디 퀀타이즈, 1마디 카운트인, 4마디 고정 녹음 |
| 녹음 형식 | 실제 AudioContext sampleRate를 따르는 float32 PCM, 마이크 기본 mono |
| 언어 | 한국어 UI 우선. 사용자 문구를 코드 곳곳에 하드코딩하지 않고 확장 가능한 사전으로 분리 |
| 디자인 | 경쟁 제품의 조작 원리를 참고하되 독자적인 화면, 아이콘 조합, 프리셋, 데모 음원을 사용 |

이 표의 트랙 수, 기본값, 출시 범위는 본 프로젝트의 설계 결정이지 경쟁 제품 사양의 인용이 아니다.

## 2. 대표 제품 조사와 반영 원칙

공식 제품 소개와 매뉴얼을 기준으로 조사했다. 판매 순위나 점유율 순위를 산정한 목록은 아니다. BOSS RC-505mkII는 소프트웨어가 아닌 하드웨어이지만, “루프스테이션다운” 연주 조작을 정의하는 비교 대상으로 포함했다.

| 비교 대상 | 공식 자료에서 확인한 관련 기능의 요약 | 프로젝트에 반영할 방향 | 출처 |
|---|---|---|---|
| BOSS RC-505mkII | 5개 스테레오 트랙, 입력/트랙 FX, Undo 계열 기능, 리듬, MIDI, 바운스와 속도 변화 | 큰 트랙 조작 버튼, 입력 FX와 재생 FX 분리, 연주 중 즉시 복구, 리듬과 컨트롤 매핑 | [S01] |
| Ableton Live의 Looper | 녹음/오버더빙, 길이 지정, 템포 연동, 다목적 버튼, Undo/Redo, 피드백, 리버스, 배속, 길이 배수 편집 | 정확한 루프 상태 전이, 박자 기반 녹음, 명확한 편집 의미와 복구 정책 | [S02] |
| Ableton Live의 Session View | 클립을 트랙에 배치하고 장면 단위로 실행하는 공연 흐름 | 클립 그리드와 같은 시점의 장면 실행, 트랙당 활성 클립 제약 | [S03] |

문서 아래의 FX 종류, 트랙 상한, 키 배치, DB 테이블, UI 수치, 테스트 조건은 이 프로젝트를 위한 독자적 요구사항이다. 특정 제품과 소리, 성능, 호환성이 같다고 주장하지 않는다.

### 2.1 웹에서 별도로 다룰 항목

| 항목 | 처리 정책 |
|---|---|
| VST/AU/AUv3 네이티브 플러그인 | 이번 순수 웹 제품의 필수 범위가 아니다. 브라우저 내장 FX와 검증된 WebAssembly DSP를 사용한다. 별도 네이티브 호스트 없이 지원한다고 표시하지 않는다. |
| ASIO, 팬텀파워, 하드웨어별 초저지연 | 브라우저 앱이 직접 제어하는 요구사항으로 잡지 않는다. 실제 장치 설정과 측정값만 안내한다. |
| Ableton Link, 전용 장비 프로토콜 | 공식 연결 방식과 웹 호환성, 라이선스를 검증하는 별도 연구 항목. 일반 BPM 동기화를 Link라고 부르지 않는다. |
| 타 사용자와 실시간 합주 | 네트워크 합주와 동시 편집은 별도 제품 범위. 클라우드는 저장과 공유 목적이며 오디오 시계가 되지 않는다. |
| 고급 보컬 자동 튜닝, 키 기반 하모니, 보코더 | 추가 연구 항목으로 유지한다. 기본 피치 시프터나 프리셋 이름 변경으로 구현 완료 처리하지 않는다. |
| 모든 브라우저의 MIDI/출력 선택 | 런타임 기능 감지 후 제공한다. MIDI가 없어도 키보드와 화면 조작으로 핵심 연주가 가능해야 한다. [S10], [S23] |
| 모바일 백그라운드 지속 연주 | 실험 결과와 운영체제 정책을 확인한 범위만 표시한다. 화면이 꺼져도 항상 녹음된다고 보장하지 않는다. |

## 3. 전체 기능 요구사항과 추적 ID

표의 `Phase`는 해당 요구사항을 주로 마무리하는 단계다. 기반 코드와 관련 테스트는 더 이른 단계에서 만들 수 있다. `조건부`는 환경 또는 사용자 설정에 따라 비활성화될 수 있다는 의미이며, 핵심 앱 전체를 막아서는 안 된다.

| ID | 기능 | Phase | 범위 | 인수 기준 요약 |
|---|---|---:|---|---|
| SYS-01 | 프로젝트 기반 | 0 | 핵심 | Next.js App Router, React, TypeScript strict, npm과 재현 가능한 lockfile을 사용한다. |
| SYS-02 | 로컬 우선 실행 | 2 | 핵심 | 로그인이나 Supabase 설정 없이 새 프로젝트, 연주, 저장, 다시 열기가 가능하다. |
| SYS-03 | 안전한 오디오 시작 | 0 | 핵심 | 사용자 클릭으로 오디오를 시작하고 권한 거부, 장치 없음, 보안 연결 문제를 각각 안내한다. |
| SYS-04 | 환경 진단 | 0 | 핵심 | 실제 sampleRate, 입력 설정, AudioWorklet, MIDI, 저장소, 격리 모드 지원 여부를 표시한다. |
| IN-01 | 입력 장치와 채널 선택 | 1 | 핵심 | 기본은 하나의 입력 장치이며 mono, stereo, L, R 입력 선택을 실제 지원 범위 안에서 제공한다. |
| IN-02 | 입력 게인과 모니터링 | 1 | 핵심 | 입력 미터, 클리핑 표시, OFF/ON/AUTO 모니터링과 음성 보정 옵션의 실제 적용 상태를 제공한다. |
| IN-03 | 녹음 지연 보정 | 3 | 핵심 | 수동 보정과 유선 루프백 측정을 제공하고 양수/음수 보정, 첫 샘플과 마지막 샘플 보존을 테스트한다. |
| CLK-01 | 공통 트랜스포트 | 1 | 핵심 | 재생, 정지, 위치 초기화, BPM 입력, Tap Tempo, 박자표, 마디/박 위치가 하나의 오디오 시계를 따른다. |
| CLK-02 | 메트로놈 | 1 | 핵심 | 강박과 약박, 볼륨, 카운트인 전용/항상 재생을 제공하며 기본 WAV 출력에는 클릭이 섞이지 않는다. |
| CLK-03 | 퀀타이즈와 고정 길이 | 1 | 핵심 | 녹음 시작/종료와 재생/정지를 즉시, 세부 박자, 마디 단위로 예약하고 취소할 수 있다. |
| CLK-04 | 첫 루프로 템포 설정 | 2 | 핵심 | 첫 자유 녹음의 길이와 선택한 마디 수로 BPM을 계산하고 반/두 배 템포 선택과 원본 보존을 제공한다. |
| CLK-05 | 장시간 동기화 | 2 | 핵심 | 서로 다른 마디 길이의 트랙이 장시간 공통 박자에 맞으며 반복마다 타이머 오차가 누적되지 않는다. |
| CLK-06 | 템포 변경 정책 | 6 | 확장 | 고정 템포, 음정도 변하는 Varispeed, 음정을 유지하는 Stretch를 명확히 구분하고 안전한 경계에서 적용한다. |
| LOOP-01 | 다중 트랙 | 2 | 핵심 | 기본 8개 트랙을 제공한다. 최종 최대 16개는 메모리와 성능 게이트를 통과한 환경에서만 활성화한다. |
| LOOP-02 | 녹음과 오버더빙 | 2 | 핵심 | Record → Play → Overdub → Play, Stop, 재시작이 실제 오디오에 작동하고 빈 루프나 무한 녹음 상태가 남지 않는다. |

### 4.2 메인 스튜디오

상단에는 프로젝트 이름, 저장 상태, 재생/정지, BPM, Tap, 박자표, 현재 마디, 카운트인, 퀀타이즈, 메트로놈, 마스터 레벨을 둔다. 항상 눈에 보이는 별도 `비상 정지` 버튼을 둔다.

중앙의 각 트랙은 이름, 색, 현재 클립, 실제 파형 축약본, 루프 진행 위치, 상태 문구, 다음 예약 동작, 큰 REC/PLAY/OVERDUB 버튼, STOP, MUTE, SOLO, UNDO/REDO, 볼륨을 갖는다. **현재 상태와 예약된 상태를 동시에 표시한다.** 예: `재생 중 / 다음 마디에 오버더빙`.

왼쪽은 프로젝트와 샘플 라이브러리, 오른쪽은 선택 트랙의 입력/FX/클립 속성, 하단은 전체 믹서와 장면을 배치한다. 필요하지 않은 패널은 접어 연주 영역을 넓힌다. 메인 연주 화면에서 페이지 이동 없이 핵심 작업을 완료할 수 있어야 한다.

화면은 어두운 배경과 명확한 대비를 기본 제안으로 삼는다. 녹음은 빨강, 재생은 초록, 오버더빙은 주황, 예약은 테두리와 카운트다운으로 표현하되 **색만으로 상태를 전달하지 않는다.** 버튼 크기는 기본 44px 이상, 주요 연주 버튼은 56px 이상을 목표로 한다. 이는 본 프로젝트의 디자인 요구사항이다.

### 4.3 트랙과 클립의 구분

- 트랙은 믹서, 입력 라우팅, FX, 솔로/뮤트의 단위다.
- 클립은 녹음된 오디오 또는 MIDI, 루프 길이, 시작 오프셋, 재생 모드의 단위다.
- 같은 트랙에서는 원칙적으로 클립 하나만 재생한다. 전환 크로스페이드 동안 두 음원이 잠시 겹치는 것은 예외다.
- 오디오 루프와 MIDI 클립을 같은 슬롯에 중복 배치하지 않는다. 트랙 `kind`로 오디오 또는 MIDI 악기 트랙을 구분한다.
- 초기 기본 패널은 트랙당 첫 오디오 클립을 보여준다. 이후 클립 그리드를 추가해도 같은 데이터와 엔진 명령을 사용한다.

### 4.4 핵심 버튼 계약

| 상태 | 메인 버튼 | STOP | UNDO/REDO |
|---|---|---|---|
| EMPTY | 입력과 용량 검사 후 녹음 예약/시작 | 아무 작업도 하지 않음 | 비활성화 사유 표시 |
| 녹음 시작 대기 | 해당 예약 취소 | 예약 취소 | 비활성화 |
| RECORDING | 정해진 종료 경계에서 Play로 전환 | 유효 구간을 확정 후 정지. 짧은 잘못된 테이크는 복구 가능한 취소 | 초기 버전은 녹음 취소를 별도 버튼으로 제공 |
| PLAYING | Overdub 예약/시작 | 선택된 정지 모드로 정지 | 이전 확정 편집으로 돌아가기 |
| OVERDUBBING | 이번 오버더빙을 확정하고 Play | 이번 오버더빙 확정 후 정지 | 현재 세션 취소는 `현재 오버더빙 취소`로 명시 |
| STOPPED | 클립을 재생 | 정지 유지 | 마지막 확정 변경을 취소/복구 |
| ERROR | 입력/저장/엔진 원인에 맞는 복구 제공 | 재생 중인 안전한 기존 트랙은 유지 가능 | 원본을 삭제하지 않음 |

메인 버튼의 기본 사이클은 `Record → Play → Overdub → Play`다. 설정으로 `Record → Overdub → Play`를 선택할 수 있지만 초기 기본값은 바꾸지 않는다. Clear는 별도 버튼이며 연주 패드의 더블클릭에 파괴적 삭제를 기본 매핑하지 않는다. 풋스위치 다중 제스처는 Phase 5에서 별도 프리셋으로 구현한다.

고정 길이 녹음은 자동 종료한다. 자유 길이 녹음은 선택한 종료 퀀타이즈에 맞춰 확정한다. 이미 큐에 있는 같은 명령을 다시 누르면 취소하고, 서로 충돌하는 새 명령은 이전 명령을 교체한 사실을 표시한다.

### 4.5 장면과 그룹

클립 실행과 Follow Action의 기능 원리는 공식 매뉴얼을 참고하되, 아래 예약과 오류 정책은 이 제품의 명시적 계약이다. [S03], [S27]

장면은 `trackId → clipId 또는 KEEP 또는 STOP` 매핑이다. 비어 있는 슬롯을 KEEP인지 STOP인지 추측하지 않는다. 기본값은 KEEP, 장면 편집에서 바꿀 수 있다. 장면 실행은 관련 트랙에 동일한 목표 오디오 프레임을 사용하는 원자적 명령으로 보낸다.

녹음 중인 트랙이 포함되면 기본적으로 장면 전환을 거부하고 종료 또는 제외를 안내한다. 자동 녹음 확정이 켜진 경우에만 원본을 안전하게 확정한 뒤 전환한다. 필요한 클립이 아직 로드되지 않았으면 일부만 실행하지 않고 전체 장면을 다음 경계로 미룬다.

그룹은 함께 시작/정지하는 그룹과 상호 배타 그룹을 구분한다. Follow Action은 `afterBars`, `action`, `target`, `repeatCount`로 저장하고 기본적으로 결정적인 결과를 낸다. 무작위 선택은 시드와 실제 실행 이벤트를 기록해 재현 가능하게 한다. 0길이 반복, 자기 자신을 즉시 무한 실행하는 설정은 거부한다.

### 4.6 단축키 기본안

| 키 | 기본 동작 |
|---|---|
| Space | 전역 재생/정지 |
| 1~8 | 해당 트랙 선택 |
| R | 선택 트랙 메인 REC/PLAY/OVERDUB |
| S | 선택 트랙 정지 |
| M / Shift+S | 선택 트랙 Mute / Solo |
| Ctrl/Cmd+Z | 앱 내 선택 트랙의 마지막 오디오/편집 동작 Undo |
| Ctrl/Cmd+Shift+Z | Redo |
| Ctrl/Cmd+S | 로컬 저장 |
| Esc | 모달 닫기 또는 예약 취소. 즉시 소리 차단과 혼동하지 않음 |
| Shift+Esc | 충돌하지 않는 환경에서 Panic의 보조 단축키. 항상 화면 버튼도 제공 |

브라우저/운영체제와 충돌하는 키는 사용자 변경을 허용한다. 입력 필드에서 타이핑하거나 IME 조합 중이면 일반 연주 단축키를 실행하지 않는다. `event.repeat`로 녹음 모드가 연속 전환되지 않게 한다. 누르는 즉시 반응해야 하는 조작에는 불필요한 더블클릭 대기 지연을 넣지 않는다.

## 5. 오디오 엔진 설계

이 절의 구체적인 엔진 구조는 본 프로젝트를 위한 설계다. Web Audio, AudioWorklet, Media API의 지원 특성은 공식 문서 [S07]~[S15], [S22]~[S24]를 참고한다. **샘플 정확도는 엔진 내부 예약의 목표이며 사용자의 클릭, 운영체제, 장치 지연까지 사라진다는 의미가 아니다.**

### 5.1 책임 분리

```text
React UI / UI Store
    ↓ 명령과 경량 설정, ↑ 상태 스냅샷
AudioEngine Facade
    ├── DeviceManager / Input routing
    ├── Transport / Command protocol
    ├── AudioWorklet: Loop DSP, 녹음, 공통 프레임 시계
    ├── Web Audio nodes: FX, 게인, 출력 라우팅
    └── Worker services: 파형, ZIP, WAV, 변환, 저장, 해시
            ↓
       IndexedDB / 선택적 Supabase
```

DOM, React, 네트워크, 오디오 PCM 처리 사이에 의존성 경계를 둔다. 실제 엔진의 상태가 권위 있는 상태다. React가 먼저 PLAYING으로 바꾸고 엔진 실행을 나중에 추측하지 않는다. UI는 `예약됨`, `실행됨`, `실패함` 이벤트를 구분해 반영한다.

권장 기본안은 **공통 Looper Worklet 하나가 활성 트랙들의 녹음/재생과 트랜스포트를 관리하고 트랙별 출력을 노출하는 구조**다. 입력은 사전에 정의된 버스에 연결한다. 입력/출력 개수와 채널은 생성 시 결정되므로 검증된 상한으로 풀을 만들고, 연주 중 노드를 임의로 재생성하지 않는다. Phase 0에서 해당 브라우저의 채널/출력 한도를 실제 검사한다. 필요하면 같은 전역 프레임 시계와 원자적 명령 계약을 유지하는 트랙별 Worklet 구조로 바꿀 수 있지만 결정과 근거를 기록한다.

### 5.2 신호 흐름과 중복 방지

```text
물리 입력 → 채널 선택 → 입력 게인 → 입력 FX
                               ├→ 선택된 트랙의 녹음 입력
                               └→ 모니터 버스 ──────────────────┐
트랙 루프 출력 → 트랙 Insert FX → Fader/Pan ────────────────┤
                                      └→ Send A/B → Return ┤
드럼/샘플러/내부 신스 → 트랙 또는 악기 버스 ────────────────┤
                                                          ↓
                                                    Program Bus
                                                          ↓
                                        Master FX → Gain → Safety Limiter
                                                          ├→ 공연 Recorder
                                                          └→ 출력 믹서 → 장치
메트로놈 → Click Bus → 클릭 볼륨 ───────────────────────────┘
```

위 흐름은 기본 정책이며 각 연결을 실제 그래프 객체와 테스트로 관리한다. 기본 공연 녹음과 WAV에는 클릭을 넣지 않는다. 클릭 포함은 사용자가 별도 선택한다. 입력 모니터는 기본 OFF이고, 같은 입력을 여러 트랙에 녹음하더라도 모니터 소리는 한 번만 출력한다. AUTO는 해당 입력을 사용하는 트랙이 녹음/오버더빙 중일 때만 모니터한다.

녹음은 입력 FX 이후, 트랙 FX 이전이 기본이다. 따라서 입력 FX는 녹음에 새겨지고 트랙 FX는 재생 시 변경할 수 있다. `Dry로 녹음`을 선택한 경우에는 입력 FX 앞에서 캡처한다. 어느 신호가 기록되는지 UI에 명시한다.

내부 바운스는 대상 트랙 자신의 출력과 클릭을 제외한다. 입력 버스, 트랙 버스, 마스터를 연결할 때 그래프의 순환을 검사한다. 딜레이 내부의 의도된 피드백 외에 사용자 라우팅으로 무제한 자기 피드백을 만들 수 없게 한다. Bypass, Mute, Solo, FX 제거는 짧은 게인 램프로 처리해 불필요한 클릭을 줄인다.

### 5.3 오디오 시작과 장치 수명

`오디오 시작` 클릭에서 AudioContext를 생성/재개한다. 오디오 재생 시작과 마이크 사용 선택은 분리해서, 마이크를 거절한 사용자도 샘플로 연주할 수 있게 한다. 마이크 요청은 HTTPS 또는 브라우저가 신뢰하는 로컬 개발 환경에서 실행하고 다음 상황을 구분한다. [S08], [S24]

`권한 거부`, `입력 장치 없음`, `다른 앱 점유 등 읽기 실패`, `요청 제약 불일치`, `권한 선택 대기`, `중간 장치 연결 끊김`을 각각 처리한다. 권한 대기 화면에는 취소가 있고, 취소 후 늦게 스트림이 도착하면 즉시 트랙을 종료한다.

음악 입력 기본 요청은 `echoCancellation: false`, `noiseSuppression: false`, `autoGainControl: false`다. 이것을 장치에 강제 적용됐다고 가정하지 않고 `getSettings()`로 실제 결과를 표시한다. 미지원 필드는 “확인 불가”로 표시한다. sampleRate는 고정 요구로 오류를 만들지 말고 실제 AudioContext 값을 권위로 사용한다.

마이크 해제, 프로젝트 닫기, 엔진 dispose 시 MediaStreamTrack, Worklet port, Worker, 이벤트 리스너와 AudioNode 연결을 정리한다. React Strict Mode와 HMR로 엔진이나 마이크가 중복 생성되지 않게 한다. 엔진은 프로젝트 편집 컴포넌트의 렌더 수명보다 상위의 클라이언트 Provider에서 관리한다.

`AudioContext`가 suspended/interrupted 상태가 되면 녹음 세션을 손상 가능 상태로 표시하고 가능한 데이터를 보존한다. 재개 후 프로젝트 위치를 확인하고 사용자 동작으로 다시 시작한다. 시간이 지나간 만큼 허위 녹음을 채워 넣지 않는다. 입력 장치 변경과 프로젝트 sampleRate 변경은 녹음 중 허용하지 않는다.

### 5.4 시간 모델과 퀀타이즈

BPM은 **4분음표 기준**으로 통일하고 박자표 분모와 혼동하지 않는다. 내부 편집 이벤트는 PPQ 960 tick을 사용하고, 오디오 처리와 캡처는 정수 sample frame을 사용한다.

```text
Fs = 실제 sampleRate
quarterSeconds = 60 / BPM
barQuarterNotes = numerator × 4 / denominator
barTicks = barQuarterNotes × 960
framesAtTick(T) = F0 + round((T - T0) / 960 × quarterSeconds × Fs)
```

이 식은 단일 템포 구간 기준이다. 템포가 바뀌면 `{startTick, startFrame, bpm}` 앵커를 가진 구간을 추가하고 이전 구간의 위상을 보존한다. `frame ↔ tick` 변환을 별도 순수 함수로 만들고 3/4, 4/4, 6/8, 7/8을 테스트한다. 6/8의 메트로놈 악센트 묶음은 별도 설정이며 BPM 의미를 몰래 바꾸지 않는다.

`round(loopDuration)` 값을 매 반복마다 더하면 소수 프레임 오차가 누적될 수 있다. 동기 루프는 원본 frame 수와 음악적 lengthTicks를 별도로 보관하고 **절대 음악 위치에서 각 경계와 재생 위상을 계산한다.** 샘플 보간 또는 분수 위상 누산으로 정수 프레임 반올림 오차를 분산한다. 자유 루프는 고정 frame 길이로 반복하고 전역 박자와 동기된다고 표시하지 않는다.

퀀타이즈 선택은 `OFF`, `1/16음표`, `1/8음표`, `1/4음표`, `1/2음표`, `1마디`, `2마디`, `4마디`, `현재 루프 경계`를 제공한다. `1/4`가 4분음표인지 1/4마디인지 불분명하게 저장하지 않는다. 내부에는 `unit: note|bar|loop`, `value` 또는 명확한 tick 값으로 직렬화한다.

명령은 엔진에 도착한 시점에서 안전하게 실행 가능한 다음 경계를 선택한다. 기본 사전 여유는 최소 두 render block을 출발점으로 측정해서 정한다. 늦게 도착한 명령을 과거에 실행한 것으로 처리하지 않는다. OFF는 가능한 다음 블록에서 실행하므로 물리 클릭과 완벽한 0ms 반응을 보장하지 않는다.

Worklet 내부에서는 `currentFrame`과 실제 출력 배열 길이로 현재 구간을 계산하고, 이벤트가 블록 중간에 있으면 앞/이벤트/뒤 구간을 나누어 정확한 위치에서 실행한다. 일정 타이머로 `audio.play()`를 매번 다시 호출하지 않는다. 반복과 메트로놈은 UI 스레드가 일시 지연되어도 진행되는 구조여야 한다. [S07], [S22]

### 5.5 명령 프로토콜과 상태

아래 TypeScript는 도메인 계약의 예시이며 그대로 완성된 라이브러리라고 간주하지 않는다. 실제 구현에서는 명령 종류별 payload를 판별 가능한 union으로 제한하고 Zod 등으로 UI/저장소 경계에서 검증한다.

```ts
type ClipState =
  | 'empty' | 'recording' | 'playing' | 'overdubbing'
  | 'stopped' | 'error';

type CommandStatus = 'accepted' | 'scheduled' | 'executed' | 'cancelled' | 'rejected';

type ScheduledCommand = {
  id: string;
  sequence: number;
  engineEpoch: string;
  projectRevision: number;
  targetTrackIds: string[];
  action: 'record' | 'play' | 'overdub' | 'stop' | 'undo' | 'redo' | 'clear' | 'scene';
  requestedGrid: { unit: 'off' | 'ticks' | 'loop'; ticks?: number };
  resolvedFrame?: number;
};
```

`pendingCommand`는 클립 상태와 별도다. `recording`이면서 `pendingStop`일 수 있다. 지연 보정의 마지막 캡처, 저장과 내보내기 상태도 오디오 상태와 별도로 관리한다. 상태 조합을 문자열 하나로 무한히 늘리지 않는다.

명령 ID와 sequence로 중복 클릭과 재전송을 제거하고 epoch로 이전 프로젝트의 늦은 명령을 폐기한다. 예약 큐의 상한은 초기 1024개를 제안하며 초과하면 명시적으로 거부한다. 자동화는 개별 샘플마다 메시지로 보내지 않고 곡선 구간/사전 이벤트 배열로 전달한다. Panic은 일반 큐를 비우고 게인 램프를 통해 안전하게 출력을 내린다.

동일 프레임의 우선순위는 `Panic → 예약 취소 → 기존 캡처 확정/정지 → 리비전 교체 → 새 클립 실행 → 새 캡처 시작 → 파라미터 변경`을 기본으로 한다. 모순된 사용자 명령은 실행 전에 해소한다. 장면 명령은 모든 대상의 준비를 확인한 후 함께 실행한다.

### 5.6 PCM 녹음과 오버더빙

핵심 루프는 float32 PCM을 사용한다. MediaRecorder는 브라우저별 컨테이너와 인코딩 선택에 영향을 받으므로 핵심 루프 데이터 모델이나 샘플 경계의 기준으로 사용하지 않는다. 선택적인 압축 공연 공유본에만 별도 사용하고 WAV라고 이름을 속이지 않는다. [S15]

입력 PCM, 기존 루프 PCM, 이번 오버더빙의 작업 버전을 분리한다. 원본은 불변 에셋이다. 새 오버더빙 전에 scratch buffer를 준비하고, 기존 루프를 통째로 실시간 콜백에서 복사하지 않는다. 큰 복사는 Worker나 사전 준비 단계에서 제한된 청크로 수행한다.

일반 Overdub의 단순화된 샘플 규칙은 다음과 같다.

```text
working[position] = previousValueAtPosition × feedback + inputSample × inputGain
```

Feedback은 0~1로 제한한다. 기본값 1이다. Overdub이 활성화된 동안 지나간 위치에만 적용하고, Play 상태에서는 반복할 때마다 감쇠시키지 않는다. Replace는 기록하는 구간의 기존 값을 새 입력으로 교체하고, 나머지 구간은 보존한다. 여러 바퀴 오버더빙했다면 해당 세션 전체가 기본 Undo 단위다.

현재 루프 출력은 새 입력을 쓰기 전의 값을 읽고, 현재 입력을 듣는 기능은 모니터 경로에서 한 번만 더한다. 새 입력을 루프 출력과 모니터에 동시에 즉시 더해 이중 출력하지 않는다. 내부 누적 신호는 float headroom을 유지하고 NaN/Infinity를 방어하며, 최종 출력 안전 처리는 별도 단계로 한다.

Undo/Redo는 새 리비전을 루프 경계에서 교체한다. 최대 10개 편집 이력을 출발점으로 하되 바이트 예산이 먼저 적용된다. 오래된 이력을 정리할 수 있어도 현재 리비전과 보장한 복구 단계는 유지한다. 안전한 원본+작업 버전 확보가 불가능하면 녹음을 시작하지 않고 용량 문제를 설명한다. 큰 버퍼를 React store의 과거 상태 스냅샷으로 복제하지 않는다.

Phase 0~3에서 역방향/변환 중 오버더빙은 안전하게 비활성화할 수 있다. Phase 6에서는 해당 상태를 순방향 작업 버전으로 명시적으로 Commit한 뒤 오버더빙하는 경로를 제공한다. 처리 전 원본은 보존하고 “준비 중”을 보여준다. 실시간 역방향 쓰기까지 지원하지 않는다면 지원하는 척하지 않는다.

### 5.7 녹음 지연 보정

`baseLatency`나 `outputLatency`를 마이크 왕복 지연의 정확한 측정값이라고 표시하지 않는다. 이 값들은 서로 다른 출력 경로 정보를 나타내며 장치 입력, 브라우저 처리, FX 지연까지 자동으로 해결하지 않는다. `getOutputTimestamp()`는 출력 시계와 화면 시계 매핑에 활용하되 입력 캡처 시각의 대용으로 단정하지 않는다. [S09], [S11], [S12]

지연 설정에는 `수동 보정값`, `유선 루프백 측정값`, `적용할 최종 보정값`, `측정 장치/입력/출력/sampleRate/관련 FX 구성`을 저장한다. 같은 지연을 기본 추정치와 실측치에서 중복 차감하지 않는다.

부호 계약은 **양수 보정값 C는 늦게 들어온 녹음을 그만큼 앞당겨 배치한다**이다.

```text
C = round(correctionMs × Fs / 1000)
alignedPosition = inputFrame - logicalRecordStartFrame - C
```

고정 N프레임 캡처에 필요한 실제 입력 구간은 `[start + C, end + C)`다. C가 양수면 마지막 샘플이 논리적 종료 시각보다 늦게 들어오므로 뒤쪽 캡처를 계속해야 한다. C가 음수면 논리적 시작 이전의 입력이 필요하므로 사전 링 버퍼가 필요하다. 사전 버퍼만 추가하고 양수 보정의 끝을 잘라 버리는 구현은 허용하지 않는다.

지연 보정 중에는 `logical playback state`와 `capture finalizing`을 구분한다. 반복 재생이 먼저 시작된다면 아직 채워지지 않은 위치에 접근하지 않는다는 것을 validity/availability 검사로 보장한다. 짧은 루프 길이가 보정값과 처리 여유보다 작으면 즉시 전환을 제한하거나 안전하게 준비 후 시작한다. 무음으로 덮어써서 정상 캡처처럼 표시하지 않는다.

루프백 측정은 유선 연결에서 테스트 펄스를 재생하고 상관관계로 지연을 찾는 별도 절차다. 낮은 음량, 피드백 차단, 측정 신뢰도, 재측정 버튼을 제공한다. 헤드폰과 스피커를 통한 수동 탭은 사람이 만든 오차가 섞이는 추정임을 표시한다. 입력/출력 장치나 sampleRate가 바뀌면 이전 보정은 재검증 필요로 표시한다.

### 5.8 클릭 없는 경계와 편집 의미

루프 경계에는 설정 가능한 2~10ms의 짧은 보간/크로스페이드를 출발점으로 사용한다. **루프의 음악적 길이는 변경하지 않는다.** 경계 전체를 잘라 루프를 줄이거나, 매 반복마다 페이드를 겹쳐 시작 트랜지언트를 없애지 않는다. 경계 처리 0ms도 선택할 수 있어야 한다.

최소 보간 재생과 부호 전환에 대한 샘플 테스트를 만들고, 드럼 어택과 지속음으로 실청취한다. 리버스, 배속, clip swap, mute, solo에는 같은 “갑작스러운 불연속 방지” 정책을 적용한다. 모든 실제 음원이 항상 완전히 무클릭이라고 보장하지 않고 경계 품질을 측정한다.

길이 2배는 소스 내용을 두 번 배치해 음악적 길이를 2배로 만드는 편집이다. 배속 2배는 재생 속도를 2배로 만드는 별도 동작이다. 절반 자르기는 기본 앞 절반을 유지하고, 다른 구간을 선택할 수 있다. 잘라낸 데이터는 Undo용 원본에서 보존한다. 자유 길이 루프의 길이 변경은 다른 트랙의 전역 템포를 바꾸지 않는다.

### 5.9 메모리와 Worker 통신

```text
PCM bytes = frameCount × channelCount × 4
```

예를 들어 48kHz 스테레오 60초 float32 PCM은 23,040,000바이트, 약 21.97MiB다. 같은 길이 8개는 약 175.78MiB이며 Undo, scratch, FX, 디코딩 사본은 별도다. 이 값은 식으로 계산한 예시이지 브라우저의 보장 용량이 아니다.

기본 PCM 작업 예산은 256MiB, 검증된 데스크톱 고급 모드는 512MiB를 제안한다. 기기 상황에 따라 더 낮출 수 있다. 트랙당 5분을 초기 길이 상한으로 두되 전체 메모리 예산이 항상 우선한다. `무제한 트랙/녹음`을 표시하지 않는다. Undo, 중간 변환, 비활성 클립, ZIP 생성까지 예산에 포함한다.

기본 경로는 **SharedArrayBuffer 없이도 동작해야 한다.** 녹음/재생은 Worklet 내부 버퍼로 계속되고, 저장/파형/외부 변환용 데이터만 사전 할당한 transferable 청크 풀로 내보낸다. 재사용할 청크는 Worker에서 돌려받는다. 아직 재생에 쓰는 ArrayBuffer를 transfer해서 detach하지 않는다. 큰 배열을 매 블록마다 `postMessage` 복사하지 않는다.

청크 풀이 소진되면 미확정 녹음을 안전하게 중단하고 복구 상태를 남긴다. 오디오 데이터를 조용히 버리고 성공이라고 표시하지 않는다. 기본 메시지 경로에서 가능한 장시간 녹음 범위는 스트레스 테스트로 정한다.

고성능 선택 경로는 SharedArrayBuffer와 Atomics 기반 링 버퍼다. HTTPS, cross-origin isolation과 관련 헤더를 검사한다. `COOP: same-origin`, `COEP: require-corp`를 적용한다면 외부 에셋, Supabase 다운로드, 인증 리디렉션과의 호환성을 검증한다. 기본 지원 경로까지 격리 모드에 의존시키지 않는다. [S13], [S22]

파형은 Worker에서 min/max 피크를 여러 해상도로 만들고 Canvas로 표시한다. PCM과 AudioNode는 UI store에 넣지 않는다. UI 상태는 10~30Hz 수준의 경량 스냅샷, 실제 화면 위치는 오디오 시각에서 계산한 보간값을 사용한다. 모든 샘플마다 React를 다시 렌더링하지 않는다.

### 5.10 이펙트 세부 계약

| 종류 | 최소 파라미터와 주의점 |
|---|---|
| Gain/Pan | dB 게인, -1~1 팬, 부드러운 변화. 음소거와 페이더 값은 별개로 보존 |
| EQ/필터 | Low shelf, Mid bell의 주파수/Q, High shelf, HPF/LPF. sampleRate의 Nyquist 범위를 넘지 않게 제한 |
| Compressor | threshold, ratio, attack, release, knee. 단순 볼륨 감소를 컴프레서로 부르지 않음 |
| Noise gate | threshold, hysteresis, attack, hold, release. 신호가 경계에 걸릴 때 덜컥거리거나 반복 개폐하지 않음 |
| Delay | 시간 또는 박자 단위, feedback 0~0.95, wet/dry, 최대 지연 길이. 탭 값 변경 시 불연속 방지 |
| Reverb | 자체 생성/허가된 IR 또는 알고리즘, decay, predelay, wet/dry. 샘플 저작권과 메모리 확인 |
| Distortion | drive, tone, output, wet/dry. 출력 게인 폭주 방지와 가능한 오버샘플링 |
| Chorus/Flanger/Phaser | rate, depth, feedback 또는 stages, wet/dry. 세 효과를 같은 처리로 이름만 바꾸지 않음 |
| Tremolo/AutoPan | rate, depth, waveform, tempo sync. 두 기능의 진폭/좌우 처리 구분 |
| Bitcrusher | 유효 비트 수, sample hold 비율, wet/dry. 필요한 DSP를 Worklet으로 구현 |
| Slicer/Stutter | 1/4~1/32음표 구간, gate/반복 패턴, momentary/toggle. 동일한 오디오 시계 사용 |
| Pitch/Stretch | transpose semitones, 속도/길이 비율, 품질 모드, 알고리즘 지연. 5.11절의 별도 품질 게이트 |
| Safety limiter | 최종 sample peak 상한, release, gain reduction 표시. 진짜 lookahead 사용 시 지연도 추적 |

`DynamicsCompressorNode`를 사용했다고 무조건 brick-wall limiter가 되었다고 주장하지 않는다. 리미터 구현을 검증하거나 제한을 명확히 표시한다. 기본 최종 sample peak 목표는 -1dBFS이며 inter-sample true peak 보장은 별도 기능이다. 음량 페이더를 올려 리미터 이후 다시 클리핑시키지 않는다. 클리핑이 보이면 원본 녹음 게인을 낮추는 안내도 제공한다.

FX 생성/제거/순서 변경은 새 그래프를 사전 준비하고 경계에서 전환한다. 첫 버전에서 녹음 중 순서 변경이 안전하지 않으면 잠금과 이유를 보여준다. 파라미터 자동화는 AudioParam 또는 Worklet의 사전 이벤트/곡선으로 연결한다. UI 값만 변하고 소리가 바뀌지 않는 FX는 미구현이다.

### 5.11 템포, 피치, 시간 변환

`Varispeed`는 속도와 음정이 함께 변한다. `Stretch`는 목표 길이에 맞추면서 음정을 유지한다. `Pitch Shift`는 길이를 유지하면서 음정을 바꾼다. 하나의 `playbackRate` 조절로 세 가지를 모두 구현했다고 보고하지 않는다.

Phase 0~3에서는 루프가 존재하는 동안 전역 템포를 잠그고 이유를 표시한다. Phase 6에서 다음 모드를 완성한다.

1. `Fixed`: 프로젝트 기준 템포 유지. 변경하려면 명시적인 변환 절차를 실행한다.
2. `Varispeed`: 동기 클립의 속도와 음정을 템포 비율만큼 함께 변경한다. 변경은 전역 마디 경계에서 원자적으로 실행한다.
3. `Stretch`: 필요한 클립을 목표 BPM에 맞춰 사전 변환하고 준비가 끝난 뒤 같은 마디 경계에서 교체한다. 준비 중 기존 템포를 유지하고 진행 상태를 표시한다.

시간 변환 후보는 공식 Web Audio/WASM 배포가 있는 **Signalsmith Stretch**다. 공식 저장소는 MIT 라이선스와 웹 배포를 안내한다. 설치 시 실제 `signalsmith-stretch` 패키지 버전, 배포 파일, API, 의존 라이선스를 재확인한다. 존재하지 않는 래퍼 API를 추측해서 호출하지 않는다. [S21]

최소 목표 범위는 시간 비율 0.5~2.0과 피치 -12~+12 semitones이며, 자연스러운 소리를 보장하는 검증 범위는 별도로 표시한다. 0.75~1.5 부근을 우선 청취한 후 극단값의 아티팩트를 평가한다. 이것은 후보 알고리즘의 완전한 품질 보증이 아니다.

첫 구현은 Worker의 사전 렌더를 허용하며 취소/진행률을 제공한다. 버전 캐시 키는 sourceHash, sourceRate, targetDurationFrames, transpose, algorithmVersion, quality로 만든다. DSP 입력/출력 지연과 flush 구간을 보정하고 요구한 길이의 결과를 정확히 만든다. 루프 경계 컨텍스트를 제공해 단발 파일의 시작/끝 아티팩트가 반복마다 생기지 않도록 한다.

실시간 스트레치는 별도 성능 게이트를 통과하면 추가한다. 녹음 중 템포 변경은 초기 고급 버전에서도 잠글 수 있지만 재생 중 사전 렌더 기반 템포 전환은 구현 대상이다. 준비에 실패하면 기존 소리와 템포를 유지한다. 원본 손실 없이 안전하게 변환하는 경로가 완료 기준이다.

### 5.12 드럼, MIDI, 자동화

드럼 시퀀서는 16/32스텝, lane별 샘플, 벨로시티, 스윙, mute/solo와 패턴 프리셋을 제공한다. 최소 자체 제작 패턴 8개와 합성 킥/스네어/하이햇을 포함한다. 모든 노트는 엔진 시각에 예약하며 스윙은 노트 위치만 바꾸고 전체 마디 길이를 바꾸지 않는다.

MIDI 클립은 `{tick, durationTicks, note, velocity, channel}`과 필요한 CC 이벤트를 저장한다. 내부 악기가 있어야 외부 MIDI 장비 없이도 피아노롤이 실제 소리를 낸다. 녹음/덮어쓰기/오버더빙, 입력 퀀타이즈와 비파괴 재생 퀀타이즈를 구분한다. 녹음 후 노트 길이와 벨로시티를 편집하고, 표준 MIDI 파일 가져오기/내보내기를 Phase 5의 세부 작업으로 포함한다. 파일 파서는 크기와 이벤트 수를 검증한다.

Web MIDI는 기능 감지와 명시적 권한 요청을 사용하고 SysEx는 기본 요청하지 않는다. Note On velocity 0의 Note Off 의미, 장치 분리, sustain 해제, 노트 종료, 모든 음 끄기를 처리한다. 장치 LED feedback은 지원되는 Note/CC 프로파일에서만 켠다. MIDI Learn과 소리를 내는 MIDI 입력 라우팅을 분리해 컨트롤용 신호가 원치 않는 음을 내지 않게 한다. [S10]

풋 컨트롤 프리셋은 단일 누름, 길게 누름, 더블 누름과 Toggle/Momentary를 지원한다. 단일 누름을 언제 확정하는지 명시하고 녹음 시작을 더블 누름 대기만큼 지연시키지 않는 기본 매핑을 제공한다. 매핑 충돌은 저장 전에 보여준다.

외부 Clock은 24 PPQN과 Start/Continue/Stop을 처리한다. 기본은 Internal Master이고, External Clock을 선택하면 BPM 추정, 지터, clock lost 상태를 제공한다. 일시적 클럭 누락 시 기존 템포를 잠깐 유지한 후 사용자에게 재동기화를 안내한다. MIDI 이벤트의 `performance.now()` 계열 시각과 오디오 시각은 재개 시마다 매핑을 다시 확인한다. 브라우저 이벤트 지연이 있으므로 물리 MIDI 입력을 sample-accurate라고 표시하지 않는다. 메시지 바이트와 채널 규칙은 공식 MIDI 메시지 표를 기준으로 검증한다. [S28]

자동화는 lane별 `off`, `read`, `touch`, `latch`를 제공한다. 기본 read에서 손으로 변경하면 일시 override 상태를 표시하고 `자동화로 돌아가기`를 제공한다. 실제 곡 이벤트는 선택한 구간 안에서 재현 가능해야 한다. 외부 MIDI로만 소리를 내는 트랙은 오디오를 다시 입력해 녹음하기 전까지 오프라인 WAV에 포함되지 않는다는 것을 명확히 표시한다.
## 6. 프로젝트 데이터와 로컬 저장

### 6.1 핵심 데이터 모델

실시간 엔진 객체를 저장하지 않고, 재구성 가능한 직렬화 모델만 저장한다. 모든 ID는 안정적인 UUID를 사용한다. 파형/변환 캐시와 원본 데이터의 수명은 분리한다.

| Track | id, kind, name, color, order, clipIds, activeClipId, inputRoute, gainDb, pan, mute, solo, inserts, sends, instrumentId |
| AudioClip | id, trackId, kind='audio', currentAudioRevisionId, sourceAssetId, sourceSampleRate, startFrame, endFrame, sourceBpm, lengthTicks 또는 freeLengthFrames, syncMode, playbackMode, rate, reverse, fade, intro/tail 참조 |
| MidiClip | id, trackId, kind='midi', lengthTicks, noteEvents, ccEvents, quantize, swing, instrumentId |

소스 오디오의 frame 좌표와 프로젝트 오디오 엔진의 frame 좌표를 혼동하지 않는다. 프로젝트를 다른 sampleRate에서 열면 원본 sampleRate를 유지하고 변환 캐시를 만든다. 원본을 덮어쓰면서 frame 좌표만 재사용하지 않는다. 클립마다 AudioRevision을 참조해 원본과 편집의 관계가 일관되어야 한다.

임의 코드, 실행 가능한 스크립트, 외부 URL, 함수 문자열은 프로젝트 포맷에 허용하지 않는다. 매크로와 액션도 허용된 명령 enum만 사용한다. `targetPath`는 허용 목록으로 검증하고 사용자 문자열로 객체 프로토타입 경로를 수정하지 않는다.

### 6.2 IndexedDB 저장소

기본 구현은 IndexedDB와 작은 래퍼 하나를 사용한다. 후보는 Dexie 또는 idb이며 하나만 고른다. 대형 오디오를 localStorage, 쿠키, React persist JSON에 넣지 않는다. 브라우저 저장소는 삭제/정리될 수 있으므로 백업이 필요하다는 문구를 보여준다. `navigator.storage.estimate()`와 `persist()`를 제공하되 영구 보관을 보장한다고 표시하지 않는다. [S14]

추천 object store는 `projects`, `projectRevisions`, `audioAssets`, `audioChunks`, `waveformCache`, `renderCache`, `recordingJournal`, `syncQueue`, `preferences`, `setlists`다. 인덱스는 projectId, updatedAt, assetId, status 위주로 실제 조회 요구에 맞춰 만든다.

녹음 청크는 `{takeId, sequence, firstFrame, frameCount, channelCount, checksum, blob}` 형태로 저장하고 시작 시 journal을 만든다. 초기 청크 크기는 채널당 8192~16384프레임을 제안하되 실제 성능으로 조정한다. 레코더가 요구하는 처리량에 맞춰 제한된 풀을 운용하고 gap/순서 누락을 검출한다.

저장 순서는 `새 오디오 청크 저장 → 에셋 검증 → 새 리비전 저장 → 현재 프로젝트의 리비전 포인터 교체`다. 앞의 단계가 실패했는데 메타데이터만 저장해 소리가 사라지는 상태를 만들지 않는다. 확정된 녹음이 저장되면 즉시 저장 상태를 갱신하고, 일반 메타데이터 변경은 약 1초 debounce를 출발점으로 사용한다.

활성 녹음을 앱 종료 직전에만 저장하지 않는다. 확정 변경은 자동 저장하고 진행 중 녹음은 청크 journal로 회복한다. 실제 보존 범위는 마지막 성공한 청크까지이며, 강제 종료 직전 데이터가 무조건 전부 복구된다고 약속하지 않는다. 마지막 청크 시각과 가능한 손실 구간을 표시한다.

동일 프로젝트를 두 탭에서 편집하면 잠금/임대권을 사용해 한쪽을 읽기 전용으로 전환한다. BroadcastChannel과 로컬 리비전 비교를 기본으로 하고, Web Locks를 쓰는 경우에는 미지원 환경 대안을 둔다. 단순 UI 잠금만 믿지 말고 저장 시 revision compare-and-swap으로 충돌을 감지한다.

### 6.3 가져오기와 검증

로컬 파일은 드래그앤드롭과 파일 선택 두 가지를 지원한다. WAV의 PCM16, PCM24, float32를 필수 지원하고, 손상된 RIFF 크기, 잘못된 channel/sampleRate, 불완전한 청크를 거부한다. 일반 압축 포맷은 실제 `decodeAudioData()` 성공 여부로 지원을 판단한다. 브라우저 지원만으로 모든 파일의 디코딩 성공을 보장하지 않는다. [S25]

압축 파일 크기만 보고 메모리가 작다고 판단하지 않는다. 디코딩 후 frame 수와 채널 수로 PCM 크기를 계산하고 전체 메모리 예산을 확인한다. 큰 WAV는 헤더 검사 후 필요한 범위만 읽는 경로를 우선하고, 압축 파일의 전체 디코딩이 너무 크면 길이 제한을 안내한다.

오디오 가져오기 완료 후 BPM, 마디 수, 루프 여부를 사용자에게 확인 가능한 값으로 표시한다. 첫 버전은 사용자가 BPM/마디 수를 지정해 동기를 맞추는 방법이 필수다. 자동 BPM/온셋 분석을 추가하면 후보와 신뢰도를 보여주고, 단순 파일 길이 계산을 음악 내용의 자동 BPM 분석으로 부르지 않는다. 사용자가 수정한 값이 우선이다.

### 6.4 프로젝트 파일 포맷

```text
project-name.loopstation.zip
├── manifest.json
├── audio/
│   └── <asset-id>.wav
├── midi/
│   └── <clip-id>.json
└── checksums.json
```

manifest에는 schemaVersion, 프로젝트 메타데이터, 트랙, 클립, FX, 장면, 자동화, 매핑, 레이아웃을 넣는다. 계정 토큰, 로컬 deviceId, 비밀키, signed URL은 제외한다. 오디오 참조는 ZIP 내부 상대 경로이며 최종 확정 버전에 필요한 에셋이 모두 포함되어야 한다. Undo 이력 포함은 선택 옵션이고, 기본 내보내기는 현재 버전과 편집 원본을 보존한다.

가져오기 전에 스키마와 에셋 해시를 검사한다. 초기 가드레일로 압축 크기 512MiB, 압축 해제 크기 1GiB, 최대 4096개 항목을 제안하되 기기의 작업 예산이 더 작으면 더 낮춘다. ZIP 크기만 아니라 총 확장 크기와 압축 비율을 제한해 ZIP bomb을 방어한다. `../`, 절대 경로, 중복 경로, 깨진 참조와 실행 파일을 거부한다.

검증이 끝나기 전 기존 프로젝트를 덮어쓰지 않는다. 새 로컬 ID로 가져오는 것이 기본이다. 같은 버전의 export → import는 음원 프레임 수, 라우팅, 장면, FX 파라미터가 동일해야 한다. 미래 schemaVersion은 임의로 파싱하지 않고 지원 버전 안내를 제공한다.

### 6.5 WAV 내보내기와 공연 녹음

내보내기에는 대상(전체 믹스/선택 트랙/스템), 구간(마디 또는 시간), 형식(PCM16/PCM24/float32), sampleRate(44.1/48kHz 및 원본), 테일 포함, 클릭 포함, dry/wet, 정규화 옵션을 제공한다. 기본은 프로젝트 rate, PCM24, 클릭 제외, 정규화 OFF다.

**구간을 반드시 명시한다.** 서로 다른 길이의 루프가 있을 때 모든 루프의 최소공배수를 자동으로 전체 곡 길이로 삼아 무제한 렌더하지 않는다. 초기 기본 구간은 8마디를 제안하고 사용자가 변경한다. 자유 루프가 있으면 초 단위 선택도 제공한다.

dry 스템은 원본 클립 출력, wet 스템은 해당 트랙 insert와 fader/pan 이후를 기본으로 정의한다. 공유 Return은 `return-A.wav`, `return-B.wav`로 별도 내보내 중복 합산을 방지한다. wet 스템에는 마스터 FX를 트랙별로 반복 적용하지 않는다. 마스터 비선형 FX가 켜진 경우 스템을 단순 합한 소리와 최종 마스터가 완전히 같지 않을 수 있음을 설명한다.

오프라인 렌더는 실시간과 같은 DSP core, 프로젝트 이벤트, 그래프 생성기를 사용한다. OfflineAudioContext와 Worklet의 조합은 지원 여부를 테스트하고, 해당 경로가 동작하지 않으면 동일 블록 DSP의 Worker renderer 또는 명시적 실시간 렌더 대안을 제공한다. 지원하지 않는 FX를 빼고 전체 믹스 성공이라고 표시하지 않는다.

Delay/Reverb 테일은 별도 길이 또는 감쇠 종료 조건으로 처리하고 상한을 둔다. WAV PCM16/24 변환 시 클리핑과 선택적 TPDF dithering을 처리하며 float32는 별도 format tag와 검증을 사용한다. 확장자를 바꾸는 방식으로 포맷 변환을 대신하지 않는다.

RIFF WAV의 크기 표현 범위를 넘는 작업은 사전에 거부하거나 여러 파일로 분할한다. RF64를 구현하지 않았으면 4GiB 이상 WAV를 지원한다고 표시하지 않는다. RIFF 청크의 4바이트 크기 필드와 헤더 오버헤드를 함께 검사한다. [S29] 인코딩과 ZIP은 Worker에서 실행하고 진행률과 취소를 지원한다.

공연 Recorder는 Program 출력의 실제 PCM을 제한된 청크로 저장한다. 새 프로젝트 열기, 녹음 중 로그아웃, 저장소 부족 시 현재 테이크를 가능한 지점까지 확정하고 상태를 남긴다. 기본 클릭 제외와 모니터 포함 정책을 UI에 명시한다. 무손실 장시간 PCM이 준비된 뒤 선택적으로 브라우저 지원 압축 공유본을 추가할 수 있다.

## 7. 선택적 Supabase 설계

### 7.1 사용 목적과 경계

Supabase는 계정, 기기 간 프로젝트 저장, 읽기 전용 공유를 위해서만 도입한다. 라이브 오디오 처리, 음원 프레임 전송, 트랙 타이밍 동기화에 사용하지 않는다. 로컬에서 클라우드로 보내는 작업은 사용자가 `클라우드에 저장`을 선택한 프로젝트만 대상으로 한다.

Auth 설정이 없는 경우 `/projects`는 로컬 프로젝트만 보여주고 로그인 기능은 숨기거나 설정되지 않았음을 표시한다. 로그아웃은 클라우드 세션을 종료하지만 로컬 파일을 임의로 삭제하지 않는다. 공용 기기 사용자를 위해 `이 기기의 프로젝트 삭제`는 별도 확인 기능으로 제공한다.

### 7.2 테이블 초안

아래는 구현할 스키마 계약이다. 실제 SQL migration, 인덱스, 제약, RLS 테스트를 작성해야 하며 테이블만 만들고 완료 처리하지 않는다.

| 테이블 | 핵심 컬럼과 제약 |
|---|---|
| profiles | id=auth.users.id, display_name, created_at. 다른 사용자의 비공개 프로필 조회 금지 |
| projects | id, owner_id, title, current_revision_id, version, created_at, updated_at, deleted_at |
| project_revisions | id, project_id, owner_id, parent_revision_id, manifest_jsonb, manifest_hash, created_at. 확정 후 불변 |
| audio_assets | id, project_id, owner_id, content_hash, storage_path, sample_rate, channels, frame_count, byte_size, state(staging/ready), created_at |
| revision_assets | revision_id, project_id, asset_id. 리비전이 참조하는 에셋 소유권과 같은 project_id를 보장 |
| renders | id, project_id, owner_id, revision_id, storage_path, format, duration_frames, byte_size, ready_at |
| share_links | id, owner_id, project_id, render_id, token_hash, expires_at, revoked_at, allow_download, created_at |
| user_presets | id, owner_id, type, name, schema_version, payload_jsonb, created_at, updated_at |

`project_id`와 `owner_id`를 중복 저장한다면 서로 다른 소유자를 끼워 넣지 못하도록 composite foreign key 또는 트랜잭션 검증을 사용한다. `projects.current_revision_id`도 같은 프로젝트의 리비전만 가리켜야 한다. JSON 내부 ID만 검증하고 DB 관계를 방치하지 않는다. 에셋 재사용은 최초에는 같은 사용자/프로젝트 내부로 제한한다.

### 7.3 Storage와 권한

프로젝트 오디오와 렌더는 private bucket에 저장한다. 경로 예시는 다음과 같다.

```text
project-audio/<user-id>/<project-id>/<asset-id>.wav
project-renders/<user-id>/<project-id>/<render-id>.wav
```

Postgres의 모든 사용자 테이블에 RLS를 켠다. 읽기/수정/삭제는 `auth.uid()`가 소유자이고 부모 프로젝트도 같은 소유자인지 확인한다. 생성과 수정 정책에는 USING뿐 아니라 WITH CHECK를 적용하고, owner_id 변경을 허용하지 않는다. 미인증 사용자 접근은 명시적으로 거부한다. [S18]

Storage에도 bucket, 사용자 prefix, 프로젝트 소유권을 확인하는 정책을 적용한다. 파일명 앞에 내 userId를 붙였다고 타인의 projectId 아래 업로드할 수 있으면 안 된다. 기존 에셋은 불변 경로로 두고 무분별한 upsert를 금지한다. MIME, 크기, frame count 메타데이터 검증을 함께 적용한다. [S19]

서버에서 세션을 확인할 때 브라우저가 보낸 owner_id를 신뢰하지 않는다. 설치된 Supabase SSR SDK의 공식 검증 방식을 따른다. 클라이언트에 publishable key를 사용하는 것은 가능하지만 비밀키와 서비스 역할 키는 서버 전용이며 꼭 필요한 관리 작업에만 사용한다. [S20]

### 7.4 동기화 프로토콜

```text
로컬 리비전 확정
→ 사용자 업로드 요청
→ 미업로드 에셋 등록(staging)
→ 직접 Storage 업로드 / 필요한 경우 재개 가능 업로드
→ 에셋 크기와 참조 검증 후 ready
→ baseVersion을 비교하는 서버 트랜잭션에서 리비전 확정
→ projects.current_revision_id와 version 갱신
→ 로컬 sync 상태 갱신
```

대형 WAV를 Next.js Server Action 본문이나 서버리스 프록시에 통째로 실어 보내지 않는다. 인증된 직접 업로드나 제한된 업로드 토큰을 사용한다. 실제 배포 서비스의 요청/시간/파일 한도를 설치 시 확인한다.

확정 API는 projectId, baseVersion, clientMutationId, manifest, assetIds를 입력받고 사용자와 모든 참조를 검증한다. `baseVersion`이 다르면 conflict를 반환하고 서버의 최신 버전과 로컬 사본을 모두 보존한다. 수정 시간만 비교하는 last-write-wins로 음악을 잃게 하지 않는다. 같은 clientMutationId 재시도는 중복 리비전을 만들지 않는다.

업로드만 성공하고 DB 확정이 실패한 에셋은 staging으로 남겨 재시도/정리한다. 사용 중인 에셋이나 다른 리비전이 참조하는 에셋을 고아 파일 정리로 삭제하지 않는다. 프로젝트 삭제도 DB와 Storage가 자동으로 함께 지워진다고 가정하지 않고 삭제 작업 상태와 재시도를 관리한다.

### 7.5 공유 링크

기본 공유는 **선택한 리비전에서 만든 읽기 전용 마스터 렌더**다. 원본 트랙, 입력 녹음, 편집 이력은 공유하지 않는다. 프로젝트 ZIP 공개는 사용자가 별도로 선택하는 후속 옵션이다.

공유 토큰은 암호학적으로 충분한 무작위 바이트로 만들고 DB에는 해시를 저장한다. 공개 화면은 서버에서 토큰 해시, 만료, 철회, 렌더 소유관계를 확인하고 짧은 수명의 접근 권한만 발급한다. share_links 전체를 공개 SELECT할 수 있게 만들지 않는다. 토큰과 signed URL은 분석 로그에 남기지 않는다.

철회 시 이후 권한 발급은 즉시 중지한다. 이미 발급한 URL은 만료 전 접근할 수 있거나 이미 받은 파일은 회수할 수 없다는 한계를 표시한다. 즉시 철회가 반드시 필요한 공유 모드는 요청마다 토큰을 검증하는 스트리밍 엔드포인트를 별도 구현한다. `다운로드 허용 OFF`를 화면에서 버튼만 숨긴다고 복제 불가능해지는 것으로 설명하지 않는다.

### 7.6 서버 API 최소 계약

| 동작 | 계약 |
|---|---|
| 프로젝트 목록/생성/복제/삭제 | 현재 사용자 범위만, 입력 스키마 검증, 삭제는 재시도 가능한 상태 처리 |
| 업로드 준비 | 소유권, 용량, 허용 형식, staging assetId 검증 |
| 리비전 확정 | 인증, baseVersion 비교, 참조 검증, 단일 DB 트랜잭션, 멱등성 |
| 공유 생성/철회 | 소유자만, 확정된 렌더만, 만료 정책, 토큰 해시 저장 |
| 공유 읽기 | 최소 메타데이터와 허가된 렌더만, 요청 제한, no-store 정책 검토 |
| 사용자 데이터 삭제 | 원본, 파생 렌더, 공유 링크, 저장소 파일을 모두 처리하고 실패 작업 재시도 |

구체적인 Next.js Route Handler 이름이나 Supabase RPC 이름은 구현 시 정하되, 클라이언트 직접 호출과 서버 호출의 보안 경계를 일관되게 유지한다. service role로 모든 요청을 처리하면서 애플리케이션 검증만 믿는 구조를 기본으로 삼지 않는다.

### 8.3 Next.js 클라이언트 경계

스튜디오의 브라우저 기능은 Client Component 경계 안에 둔다. Server Component는 초기 메타데이터/앱 셸만 담당한다. “use client”를 붙였다는 이유로 모듈 최상위의 window 접근이 언제나 안전하다고 가정하지 않는다. 브라우저 객체 생성은 명시적인 클라이언트 lifecycle과 사용자 동작에서 한다. [S16], [S17]

AudioEngine을 서버 전역 singleton으로 만들지 않는다. AudioContext, AudioNode, MediaStream, IndexedDB handle을 Server Component props나 JSON으로 넘기지 않는다. 공유 페이지는 편집 엔진 전체를 내려받지 않는 가벼운 플레이어로 분리한다.

`audioWorklet.addModule()`은 소스 `.ts` 파일이 아닌 실제 배포된 JS URL을 받는다. Worklet 번들은 Node 내장 모듈, React, Next 서버 API, 해석되지 않는 npm bare import를 포함하지 않는다. WASM도 상대 경로와 MIME/CORS를 검증한다. dev 서버에서는 되는데 production build에서 404가 나는 상태를 테스트로 잡는다.

### 8.4 npm 명령 계약

빈 저장소에서는 설치 시점의 공식 `create-next-app` 옵션을 확인해 npm으로 생성한다. 이미 문서가 놓인 폴더를 CLI가 거절하면 사용자 파일을 삭제하지 말고 임시 scaffold에서 필요한 코드만 병합하거나 수동 초기화한다. 생성기가 만든 AGENTS.md와 이 프로젝트 규칙이 충돌하면 핵심 프로젝트 규칙을 보존해 통합한다. [S16], [S26]

버전 확인 후 실제 버전을 lockfile과 PROGRESS에 남긴다. 자동으로 매번 `latest`로 업그레이드하지 않는다.

```bash
node --version
npm --version
npm view next version engines
npm view react version
npm view react-dom version
```

구현할 스크립트 계약은 다음과 같다.

```json
{
  "scripts": {
    "dev": "<Worklet 최초 빌드 및 watch와 next dev를 함께 실행>",
    "build:audio": "node scripts/build-audio.mjs",
    "build": "npm run build:audio && next build",
    "start": "next start",
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "test:watch": "vitest",
    "test:audio": "vitest run tests/audio",
    "test:e2e": "playwright test"
  }
}
```

위 `dev`의 꺾쇠 문구는 실행 명령이 아니라 요구사항이다. Codex는 운영체제 호환성을 고려한 실제 명령으로 구현해야 한다. Worklet 변경 시 dev에도 최신 번들이 반영되고 build에도 누락되지 않아야 한다. lint는 설치된 Next.js 버전이 지원하지 않는 구형 명령을 추측하지 말고 ESLint를 직접 실행한다. 빈 테스트 파일이나 항상 성공하는 스크립트를 만들지 않는다.

### 8.6 배포와 PWA

실제 호스팅 대상은 사용자가 선택하기 전까지 고정하지 않는다. HTTPS, Worklet 정적 URL, WASM MIME, CORS/CSP, 클라우드 SSR 환경변수, 장치 권한을 production 모드에서 검증한다. 결제/유료 플랜 생성을 자동 실행하지 않는다.

PWA는 편의 기능이다. 먼저 네트워크 없는 상태에서 로컬 프로젝트와 준비된 에셋이 동작하게 한 뒤 app shell과 오디오 번들을 캐시한다. 인증 응답, 공유 토큰, signed URL과 private 다운로드를 무차별 캐시하지 않는다. 브라우저 오프라인 캐시와 IndexedDB 프로젝트는 다른 저장 계층이다.

서비스워커 업데이트는 연주나 녹음을 강제로 새로고침하지 않는다. 업데이트 준비를 표시하고 안전한 시점에 사용자가 적용한다. 배포 버전과 DSP/Worklet 메시지 스키마가 맞지 않으면 오류를 표시하고 기존 저장 데이터는 보존한다. 화면 숨김, 전원 절약, OS 오디오 중단에 대한 보호와 복구를 제공하되 브라우저의 동작을 앱이 무조건 막을 수 있다고 주장하지 않는다.
## 9. 단계별 구현 계획

개발 순서와 바로 다음 작업은 [개발 계획 폴더](plan/README.md)와 [다음 작업](plan/NEXT.md)에서 관리한다. 이 명세는 상세 계약과 인수 기준을 유지하고, 실제 구현·검증 증거는 [진행 기록](PROGRESS.md)에 남긴다.

**중간 출시 구분:** Phase 0~3은 기본 루핑 제품, Phase 4~6은 고급 연주 기능, Phase 7은 선택적 클라우드, Phase 8은 전체 출시 검증이다. 핵심 기능이 동작해도 확장 요구사항을 남겨 둔 상태를 “전체 완료”로 표시하지 않는다.

각 단계는 `도메인/엔진 → 최소 UI → 실제 오디오 또는 파일 → 자동 테스트 → 수동 검증 → 문서 갱신`의 작은 수직 단위로 진행한다. 한 단계가 크면 요구사항 ID별 작업으로 더 나눈다. 전 단계의 치명적인 오디오/저장 문제가 남아 있으면 다음 기능을 덧붙이기 전에 수정한다.

### Phase 0. 저장소 점검과 실제 오디오 기반

기존 파일과 package.json을 확인하고 Next.js/React/npm 기반을 만든다. 환경 진단, 사용자 클릭 기반 AudioContext, 마이크 선택/거부 UI, 모니터링 OFF, Worklet build pipeline, 순수 frame/tick 변환 함수와 테스트를 만든다.

**실행 결과:** 스튜디오 셸에서 자체 테스트 신호가 실제 Worklet을 통과하고, 마이크 권한을 거부해도 데모 경로를 사용할 수 있다. production build에서도 Worklet URL이 로드된다. 이 단계의 임시 신호는 개발/데모 모드로 표시한다.

**통과 조건:** lint/typecheck/test/build, 실제 브라우저 Worklet 로딩, 중복 AudioContext 방지, dispose 동작. 아직 루핑/FX/클라우드를 구현한 것으로 표시하지 않는다.

### Phase 1. 한 트랙의 녹음과 정확한 반복

입력 장치/채널, 입력 미터와 모니터, 한 트랙 PCM 캡처, 고정 길이 녹음, 첫 반복 전환, Play/Stop, BPM, 박자표, 메트로놈, 카운트인, 기본 퀀타이즈를 구현한다. 녹음 최대 길이, 취소, 권한/장치 끊김을 처리한다.

**실행 결과:** 사용자가 4마디를 녹음하면 실제 소리가 박자에 맞춰 반복되고 STOP으로 멈춘다. 신호가 없는 녹음도 데이터와 상태가 정상 처리된다.

**통과 조건:** 44.1/48kHz fixture의 지정 frame 수, 정해진 경계에서 전환, 클릭이 기본 녹음 데이터에 섞이지 않음, 재생 반복이 React 타이머에 의존하지 않음.

### Phase 2. 8트랙, 오버더빙, 복구 가능한 기본 제품

트랙 관리, 길이가 다른 루프의 공통 시계, 메인 버튼 상태 머신, 오버더빙 세션, Undo/Redo/Clear, 트랙 믹서, 단축키, 첫 자유 루프의 템포 설정을 추가한다. IndexedDB 에셋/리비전과 자동 저장, 자체 데모 프로젝트를 연결한다.

**실행 결과:** 8개 트랙에서 소리를 쌓고 선택 트랙의 마지막 오버더빙만 취소할 수 있다. 새로고침 후 확정된 루프가 복구된다. 이 기능은 로그인 없이 동작한다.

**통과 조건:** 단순 합성 입력으로 A+B 및 Undo→A를 검증하고 1/2/4/8마디 동기를 테스트한다. 저장 실패 시 저장 완료 표시를 하지 않는다. 메모리 예산을 초과하는 추가 녹음을 거부한다.

### Phase 3. 편집, 지연 보정, 파일 입출력

입력 지연 보정, 파형 편집, Loop/One-shot/Gate, 시작/정지 방식, 자유 루프, 리버스/배속, 길이 배수 편집, 공연 모드와 Panic을 구현한다. WAV 가져오기, 프로젝트 ZIP, 믹스/스템 WAV, 복구 journal, 다중 탭 충돌을 완성한다.

**실행 결과:** 실제 마이크로 만든 프로젝트를 저장하고 ZIP으로 다른 브라우저에 옮겨 재생하거나 WAV로 내보낼 수 있다. 변환 중 오버더빙 등 아직 미지원 조합은 이유를 표시한다.

**통과 조건:** 지연 보정의 양수/음수와 끝부분 보존, WAV 헤더/샘플 검증, ZIP 왕복, 누락 에셋/손상 파일/용량 부족 처리, 비상 정지 후 안전한 재개.

### Phase 4. FX, 장면, 내부 녹음

입력/트랙/마스터 FX 랙, 기본 EQ/필터/다이내믹, Delay/Reverb/Distortion, Send/Return, Replace/Feedback, 임계값 녹음, 최근 연주 가져오기를 만든다. 여러 클립과 장면/그룹, 내부 바운스, PCM 공연 녹음을 연결한다.

**실행 결과:** 다른 클립 조합을 같은 마디에서 실행하고, 실제 FX를 거친 소리를 공연 WAV로 남길 수 있다. 기존 루프 위에 새 녹음을 교체하거나 감쇠시키는 규칙이 작동한다.

**통과 조건:** 장면 전환 원자성, 모니터 이중 출력 방지, 바운스 자기 피드백 차단, 클릭 제외, FX 파라미터의 실제 오디오 변화, 공연 청크 누락 감지와 복구.

### Phase 5. 컨트롤, 리듬, 곡 구성

드럼 패턴, 샘플 패드, 자체 내부 악기, MIDI 클립/피아노롤/파일 입출력, 키보드/MIDI Learn, 풋 컨트롤, 장치 프로파일을 구현한다. Follow Action, 연주 이벤트 타임라인, 자동화, FX 프리셋, 매크로, 사용자 지정 화면과 세트리스트를 추가한다.

**실행 결과:** 마이크 없이도 드럼과 MIDI 악기로 루프를 만들고, 컨트롤러 또는 화면으로 장면/효과를 제어하며 곡 순서를 재생할 수 있다.

**통과 조건:** 장치 분리 시 stuck note 방지, MIDI 없는 환경의 내부 악기 동작, 자동화 재현, 무한 Follow Action 방지, 편집 잠금, 레이아웃/매핑 저장 왕복. 실제 MIDI 장비 미보유 시 해당 검증만 미실행으로 남긴다.

### Phase 6. 고급 DSP와 고급 루프

독립 시간/음정 변환, 재생 중 안전한 BPM 전환, 변환 클립을 Commit한 후 오버더빙, 인트로/테일, 연주용 변조 FX를 완성한다. 지원 브라우저/장치에서 외부 MIDI Clock을 검증한다. 최대 16트랙과 고급 메모리 모드는 검증 후 개방한다.

**실행 결과:** 음정을 유지한 템포 변경과 길이를 유지한 음정 변경을 구분해 실제 오디오로 들을 수 있다. 처리 준비가 끝나기 전에는 기존 연주가 유지된다.

**통과 조건:** 독립 변환 주파수/길이 테스트, 보컬/드럼/코드의 실청취, 루프 경계와 DSP 지연 보정, WASM 재현 가능한 빌드/배포, 알고리즘 라이선스, 변환 실패 시 원본 유지. 품질 미충족은 명시적 차단 항목이다.

### Phase 7. Supabase 클라우드 기능

사용자가 계정/기기 간 저장/공유를 사용할 때 활성화한다. Auth, 스키마 migration, RLS, private Storage, 리비전 동기화, 충돌 사본, 공유 링크와 삭제 처리를 구현한다.

**실행 결과:** 동일 사용자가 다른 기기에서 선택한 프로젝트를 가져오고, 다른 사용자에게는 선택한 마스터 렌더만 공유할 수 있다.

**통과 조건:** 미인증/사용자 A/사용자 B 권한 테스트, 에셋 업로드 실패 후 복구, baseVersion 충돌, 공유 만료/철회, 원본 비공개, 로그와 ZIP에 키/토큰 없음. 환경변수가 없어도 로컬 모드는 계속 실행된다. 실제 Supabase 환경에서 검증하지 않았다면 클라우드 검증 완료로 표시하지 않는다.

### Phase 8. 출시 검증과 사용성

주요 데스크톱 브라우저 실측, 터치/작은 화면, 접근성, 저장소 부족/새로고침/장치 교체, 장시간 연주와 export 중 부하를 테스트한다. 필요한 PWA와 업데이트 보호를 추가하고 실제 배포 환경을 검증한다.

**실행 결과:** 지원 환경, 조건부 기능, 실제 검증값, 알려진 제한을 제품 안과 진행 문서에 표시한다. 미구현 버튼이나 성공하는 척하는 동작이 남지 않는다.

**통과 조건:** 10절의 테스트 결과와 모든 요구사항 ID 상태를 대조한다. 전체 완료는 64개 요구사항을 구현/검증하거나 조건부 처리 근거를 명시했을 때만 선언한다. 선택하지 않은 클라우드나 미지원 장치 기능을 구현 완료 수에 합산하지 않는다.

| AUDIO-15 | 440Hz 테스트 음을 길이 유지 +12 semitones | 목표 길이를 유지하며 주 주파수는 880Hz 부근이다. 측정 창과 허용 편차를 보고한다. |
| AUDIO-16 | 440Hz 테스트 음의 길이를 1.25배로 Stretch | 목표 frame 길이로 변환되고 주 주파수는 440Hz 부근이다. 리샘플링만 한 구현을 통과시키지 않는다. |
| AUDIO-17 | FX 각 종류의 파라미터를 변경 | 대응하는 레벨/스펙트럼/시간 특성이 실제로 달라지고 NaN, Infinity, 폭주가 없다. |
| AUDIO-18 | 안전 리미터 입력 과다 | 설계한 sample peak 상한을 지킨다. true peak 보장 여부는 별도 표시한다. |
| AUDIO-19 | 바운스/공연 녹음/마스터 믹스 | 라우팅 대상이 정확하고 자기 피드백이 생기지 않으며 클릭 포함 옵션이 일치한다. |
| AUDIO-20 | 입력 장치 분리 또는 context suspend | 현재 테이크의 상태와 복구 범위를 표시하고 기존 확정 에셋을 보존한다. |
| AUDIO-21 | MIDI Stop/장치 분리/프로젝트 교체 | 내부 음원과 외부 MIDI의 남아 있는 노트를 가능한 범위에서 종료한다. |
| AUDIO-22 | 변환 실패 또는 FX 그래프 준비 실패 | 기존 클립과 템포가 유지되고 다음 동작을 안전하게 취소한다. |

DSP 수치 테스트는 실제 샘플 프레임을 확인한다. 화면의 타이머가 정확해 보인다는 이유로 통과시키지 않는다. hardware round-trip과 CPU 안정성은 환경별로 별도 측정해야 한다.

### 10.3 파일과 복구 테스트

`DATA-01`: 녹음 → 자동 저장 → 새로고침 → 로드 후 frame 수/에셋 해시/트랙 설정이 동일하다.

`DATA-02`: 프로젝트 ZIP export → 새 로컬 프로젝트 import 후 소스 오디오, 장면, 매핑, FX, 자동화의 왕복이 일치한다.

`DATA-03`: PCM16/24/float32 WAV의 헤더, sampleRate, 채널 수, 파일 길이, 실제 PCM을 독립 파서로 검증한다. dry/wet/클릭/테일 설정이 일치한다.

`DATA-04`: 공유 Return을 포함한 스템을 선형 test bus에서 합했을 때 같은 조건의 믹스와 비교한다. 마스터 비선형 FX를 트랙마다 중복 적용한 경우를 검출한다.

`DATA-05`: 쿼터 초과, 저장 거절, 중간 업로드 실패, 손상 청크, 깨진 checksum에서 원본을 보존한다. 임시 오디오만 저장된 경우 복구 안내가 나온다.

`DATA-06`: 녹음 중 브라우저를 닫은 상황을 모사해 마지막 성공 청크까지 복구하고 손실 가능 구간을 표시한다.

`DATA-07`: 같은 프로젝트를 두 탭 또는 두 기기에서 수정했을 때 충돌을 발견하고 두 버전을 보존한다.

`DATA-08`: 대형 파일, ZIP bomb, 경로 탈출, 불법 스키마, 과도한 이벤트 수, 실행 코드 문자열을 거부한다.

`DATA-09`: 미래 schemaVersion 파일은 안전하게 거부한다. 지원되는 과거 버전은 원본 백업을 만든 뒤 migration한다.

`DATA-10`: 에셋 정리 시 현재 리비전, Undo 보존 범위, 다른 참조 프로젝트에 필요한 파일이 삭제되지 않는다.

### 10.4 Supabase 권한 테스트

미인증 사용자, 사용자 A, 사용자 B를 따로 준비한다. B는 A의 프로젝트, 리비전, 원본 에셋, 렌더, 프리셋, Storage 경로를 읽거나 수정할 수 없어야 한다. 자신의 owner_id와 타인의 project_id를 혼합한 INSERT/UPDATE도 실패해야 한다.

서버 확정 API의 잘못된 baseVersion, 타인 assetId, staging asset, 삭제된 부모 프로젝트, 중복 clientMutationId를 각각 검증한다. Storage 정책과 DB 정책을 따로 검증하고 UI에서 숨겼다는 이유로 권한 통과 처리하지 않는다.

공유는 정상 토큰, 틀린 토큰, 만료, 철회, 렌더 삭제, 다른 사용자 렌더 참조, 직접 Storage URL 접근을 검사한다. 토큰 해시 목록과 원본 프로젝트가 공개 API로 노출되지 않아야 한다.

### 10.5 브라우저와 성능 기준

| 환경 | 목표와 표시 정책 |
|---|---|
| 데스크톱 Chrome/Edge | 첫 출시의 주 검증 환경. 실제 버전/OS/CPU/메모리/오디오 장치를 기록한다. |
| 데스크톱 Firefox/Safari | 오디오, 파일, 저장, MIDI, 출력 선택을 기능별로 검사한다. 통합테스트가 없으면 “완전 지원”으로 표시하지 않는다. |
| iOS Safari/Android Chrome | 우선 4트랙 저부하 모드로 검증한다. 권한, 터치, 외부 장치, 화면 잠금/복귀를 확인한다. |
| 자동화 환경 | headless 결과는 엔진/파일/화면 검증이다. 실제 스피커나 인터페이스의 저지연 실측으로 대체하지 않는다. |

기본 스트레스 시나리오는 **48kHz, mono 8트랙, 각 16마디, 120 BPM, 공통 FX와 Send 2개, 10분 연주**다. 프로젝트 메모리, 버퍼 풀, 명령 지연, 저장 backlog, UI 반응, 오디오 끊김 징후를 기록한다. 전체 공연 녹음과 WAV 내보내기를 동시에 실행하는 추가 시나리오를 둔다.

빠른 CI에서는 축소된 30~60초 시나리오를 사용하고, 출시 검증에서는 긴 시나리오를 별도로 실행한다. 최대 16트랙은 8트랙 결과에서 추측하지 말고 실제 조건으로 검증한다. 장치별로 지원 가능한 설정이 다르면 low-power/balanced/high-performance 프로파일과 제한 이유를 보여준다.

초기 성능 목표는 예약된 DSP 이벤트의 프레임 오차 1프레임 이내, 기준 환경에서 10분간 복구 불가능한 청크 누락 0건, 메모리 예산 준수다. 일반 UI 동작은 100ms 내 피드백을 목표로 한다. 이것은 목표값이며 측정 전 광고 문구로 사용하지 않는다. 하드웨어 왕복 지연에는 하나의 보장 숫자를 정하지 않는다.

CPU 수치를 읽을 수 없는 환경에서는 임의의 퍼센트를 만들어 보여주지 않는다. 명령 지연, 큐 길이, 저장 지연, 처리 오류 등 측정 가능한 지표를 `처리 부하 추정`으로 명시한다. 브라우저가 주는 메모리/오디오 진단 API는 기능 감지 후 사용하고 없으면 미측정으로 남긴다.

### 10.6 완료 정의

기능 완료는 실제 사용자 조작, 실제 음원/파일 결과, 관련 자동 테스트, 실패 흐름, 저장/복구, 진행 문서 기록까지 충족한 상태다. 고급 기능과 조건부 기능은 완료/부분 구현/미검증/환경 제한을 구분한다.

최종 출시 전에는 버튼별 동작을 전수 확인한다. 비어 있는 onClick, 모든 FX가 같은 소리인 프리셋, 실제 저장 없이 성공하는 토스트, 소리 없는 MIDI 피아노롤, 임의로 움직이는 미터, MediaRecorder 확장자만 바꾼 WAV, 항상 0인 latency/CPU 표시가 있으면 출시를 막는다.

CI 검증 결과와 별도로 실제 마이크, 헤드폰 또는 인터페이스를 사용한 청취 결과를 기록한다. 장비가 없어 검사하지 못했으면 정확히 그렇게 적는다. “빌드 통과”와 “실제 연주에 적합함”을 같은 의미로 사용하지 않는다.

## 11. 위험과 구현 결정 기록 원칙

가장 높은 우선순위는 타이밍, 소리 끊김, 데이터 유실, 입력 피드백이다. 화려한 시각 효과와 계정 기능은 이 문제를 가리는 수단이 아니다.

| 위험 | 조치 |
|---|---|
| 메인 스레드 렌더 부하 | DSP/시계 분리, UI 스냅샷 빈도 제한, Waveform Worker |
| 큰 녹음과 Undo의 메모리 사용 | 사전 byte 예산, 불변 원본, 제한된 scratch/청크 풀, 단계적 편집 준비 |
| sampleRate/지연/브라우저 차이 | 실제 값 확인, 별도 보정, signed offset 테스트, 기능별 지원 표시 |
| 음향 피드백과 이중 모니터 | 기본 monitor OFF, 한 번만 모니터, 안전 게인, 라우팅 순환 차단 |
| 시간 변환의 음질 저하 | 검증된 DSP 후보, 원본 유지, 변환 품질 범위 표시, 실청취 |
| 저장 중 강제 종료 | 지속 청크 journal, 원자적 리비전 교체, 손실 구간 안내 |
| 클라우드 업로드와 충돌 | staging/ready, 재시도, 멱등성, baseVersion 비교, 사본 보존 |
| 큰 프로젝트 명세를 한 번에 구현 | 요구사항 ID별 수직 구현, 단계별 게이트, 실제 결과 기반 진행 문서 |
| 외부 코드/음원의 사용 권한 | 의존성별 라이선스 확인, 허가된 데모 에셋, 자체 프리셋 |

구현 중 명세 변경이 필요하면 이유, 대안, 영향받는 요구사항 ID, 사용자에게 보이는 제한, 검증 결과를 PROGRESS의 결정 기록에 남긴다. 기능을 삭제하거나 다른 스택으로 바꾸는 결정을 문서 갱신 없이 진행하지 않는다. 비밀키나 유료 서비스가 없다는 이유로 로컬 오디오 개발을 멈추지 않는다.
